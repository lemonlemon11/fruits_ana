## ADR-001 — 使用 MySQL 作为唯一业务库

- Date：2026-09-09
- Status：Accepted
- Context：原型阶段以 SQLite 文件 + CSV 产物验证口径；正式系统需要并发访问、事务与
  多端共享数据。
- Decision：业务数据统一存 MySQL，应用通过 SQLAlchemy 2.0 + PyMySQL 访问。
- Why：1) 需要事务与并发写入；2) 需要长期运行的服务端存储；3) 已有 SQLite → MySQL
  迁移工具可平滑过渡。
- Alternatives：继续使用 SQLite（不采用：并发与部署形态不满足）；CSV/Excel 作为主存储
  （不采用：无法支撑查询与一致性）。
- Consequences：优点是可部署为服务并支持多人使用；缺点是引入了数据库运维与迁移成本，
  schema 变更必须配套可重复执行的迁移脚本。迁移工具见 `backend/scripts/migrate_sqlite_to_mysql.py`。

## ADR-002 — BC 等级归入 C 级

- Date：2026-09-08
- Status：Accepted
- Context：结算单品种规格存在 A / B / C / BC 四种等级标识，报表需要统一分级。
- Decision：`BC` 归入 `C`，界面显示为「C 果（含 BC）」。
- Why：历史报表标题「C 果（C/BC 级）」佐证口径一致。
- Consequences：导入后 `sale_record` 不再保留 BC 独立等级；展示文案需保持一致。

## ADR-003 — 第一期不做利润测算

- Date：2026-09-08
- Status：Accepted
- Context：最终目标包含利润测算，但当前没有采购成本与国内物流/报关费用数据。
- Decision：第一期只做存量销售数据的存档、导入与可视化；利润测算留待第二期，且必须先确认
  成本数据口径。
- Consequences：数据模型需为后续成本维度留出扩展空间，但不得凭空臆测字段结构。

## ADR-004 — 数据接入方式为整批文件上传

- Date：2026-09-08
- Status：Accepted
- Decision：用户维护 Excel/CSV 文件，通过 `/api/imports` 整批上传；暂不做粘贴文本解析或逐条表单录入。
- Consequences：解析器需兼容多种结算单版式（柜号在表头上方、日期合并、等级写在品种规格中）。

## ADR-005 — 认证采用服务端会话 + HttpOnly Cookie

- Date：2026-09-09
- Status：Accepted
- Context：需要登录才能访问业务页，但系统为单体应用、无第三方 OAuth 需求。
- Decision：使用 Argon2 哈希密码；登录后创建服务端会话，数据库只保存 token 的 SHA-256 哈希，
  浏览器通过 HttpOnly Cookie `fruit_session` 携带凭证，有效期 7 天。
- Why：1) 会话可服务端撤销（登出/失效）；2) Cookie 无法被前端 JS 读取，降低 XSS 窃取风险；
  3) 无需引入 JWT 签名密钥与刷新令牌机制。
- Alternatives：JWT（不采用：撤销成本高、需要额外密钥管理）；前端 localStorage 存 token
  （不采用：XSS 风险更高）。
- Consequences：水平扩展时需要共享会话存储；跨域部署需调整 Cookie 策略。

## ADR-006 — 指标口径以「金额 ÷ 数量」为准

- Date：2026-09-09
- Status：Accepted
- Decision：销售数量取 `quantity` 之和；销售金额取 `amount` 之和；加权均价 = 销售金额 / 销售数量，
  数量为 0 时返回空值；数量占比 = 某等级数量 / 同筛选范围总数量；日期筛选按销售日期计算。
- Consequences：所有新增报表必须复用同一口径，禁止在视图层重新定义平均值。

## ADR-007 — 前端不引入图表库与 UI 组件库

- Date：2026-09-09
- Status：Accepted
- Context：图表形态固定（趋势线、占比饼图、对比柱状），且需要适配移动端与换肤。
- Decision：图表以手写 SVG 组件实现，样式使用项目内 CSS 变量与 `styles-*.css`。
- Why：避免额外依赖体积与样式冲突，便于精确控制移动端布局与主题变量。
- Consequences：新增图表需要自行实现，改动时注意移动端断点与主题变量一致性。

## ADR-008 — 以「商号」作为结算单业务唯一键

- Date：2026-09-10
- Status：Accepted
- Context：柜号不唯一（637 与 640 两张结算单共用柜号 CBHU2970762），单号为客户侧编号且可能重复，
  仅用柜号会导致分析口径混淆；商号是我司记录的商业合同唯一单据号。
- Decision：`import_batch` 承担结算单职责并持有唯一业务键 `merchant_no`（商号），
  同时保存 `order_no`（单号）、`container_no`（柜号，可为空）、`vehicle_no`（转运车号）；
  分析、导出、前端全部以商号作为查询与归集维度，`sale_record` 不再保存柜号。
  同一商号再次导入默认返回 `conflict`，用户确认后以覆盖方式替换整张结算单。
- 界面约定：下拉框按**「商号（单号）」**展示（如 `商号 640（宝贝L004）`），取值仍为商号（唯一键）。
  2026-09-10 客户再次确认「商号才是唯一的，单号也近似唯一但存在重复」后，展示顺序由
  「单号（商号）」调整为商号在前，避免重复柜号或重复单号造成误选；
  筛选字段名与占位文案同步由「单号 / 选择单号」改为「商号 / 选择商号」
  （表格里的「单号」列仍指单号本身，不受影响）。
- Why：1) 商号来自我司合同，业务上唯一且可追溯；2) 柜号可能缺失或重复，不适合做身份；
  3) 覆盖式导入保证「一张商号 = 一份最新结算单」，避免同一张单据出现多份明细。
- Alternatives：以单号 `settlement_no` 作唯一键（不采用：单号为客户侧编号，规则上允许重复）；
  以柜号作唯一键（不采用：已证明重复且可能缺失）。
- 依据文档：`docs/superpowers/specs/2026-09-10-merchant-number-dimension-design.md`、
  `docs/superpowers/plans/2026-09-10-merchant-number-dimension.md`；
  早期「单号唯一键」方案（`2026-09-10-settlement-number-identity-*`）已被本条目取代。
- Consequences：`sale_record.container_id/container_name`、`container_summary` 表已废弃，
  线上库需执行 `backend/scripts/backfill_settlement_identity.py` 完成表结构迁移与商号回填（含 SQL 快照）。

## ADR-009 — 系列从单号中文前缀识别，对比口径为「元/件」

- Date：2026-09-10
- Status：Accepted
- Context：「系列对比」需要把结算单归到系列（如 `宝贝01`、`宝贝02`、`宝贝003`、`宝贝L004` 同属「宝贝」），
  但结算单里没有独立的系列字段；同时各系列箱重不同（宝贝为 17 / 19 / 19.5KG 混装），
  跨系列用「元/件」还是「元/KG」需要拍板。
- Decision：
  1. 系列由结算单**单号**（`order_no`）开头连续的中文前缀推导；识别不出时归入「未识别系列」，不阻塞对比。
  2. 对比主体是结算单（商号唯一键），系列仅作分组与汇总；用户按业务单勾选，支持同系列内和跨系列对比。
  3. 均价口径统一为「销售金额 ÷ 件数」（元/件），与全站口径一致；本期不做元/KG 换算。
  4. 一次最多勾选 6 张结算单（前端限制），保证图表可读。
- Why：1) 单号是现有数据中唯一能稳定体现系列归属的字段；2) 用户明确选择元/件口径；
  3) 不新增字段、不改库，可立即上线，后续再考虑维护系列别名字典。
- Alternatives：新增 `brand` 表与人工维护别名（不采用：需要额外维护成本与一次迁移，本期无必要）；
  从文件名识别系列（不采用：文件名可随意修改，不可靠）；元/KG 口径（不采用：需要新增重量解析与回填，
  且用户已确认元/件）。
- Consequences：
  1. 单号命名不规范（如 `626`）会落入「未识别系列」，需要在导入时人工确认单号。
  2. 空值/异常写入不会抛错，但系列名可能不等于业务预期品牌名。
  3. 元/KG 对比、AI 分析结论、Excel 导出不在本期范围，见 `docs/TODO.md`。
- 依据文档：`docs/superpowers/specs/2026-09-10-brand-series-analysis-design.md`（含本次修订段落）。

## ADR-010 — 界面日期统一显示为「到达日期」

- Date：2026-09-10
- Status：Accepted
- Context：用户口述口径为「日期统一叫到达日期就行」。此前界面同一字段存在
  「销售日期」「首销日期」「日期」「销售周期」多种叫法，且筛选控件写作「开始日期 / 结束日期」，
  同一页里出现多种叫法，用户难以判断查的是哪一天。
- Decision：结算单日期在**界面上一律显示为「到达日期」**，具体包括
  表头（结算单列表 / 结算单明细 / 数据明细 / 趋势表 / 系列总览）、筛选控件
  （统一为「到达日期起」「到达日期止」）、区间说明与空状态文案（如「到达日期：8/27 至 9/05」）。
  数据层不变：数据库字段仍为 `sale_record.sale_date`，接口参数仍为 `start_date` / `end_date`，
  解析仍按源表 `销售日期 / 日期 / 销售时间` 表头识别。
- Why：1) 该日期在业务上就是货物到达日期，用户以此对账；2) 同一字段多种叫法会让果农误判；
  3) 只改文案不改字段，零迁移、零接口变更，风险最低。
- Alternatives：改库字段名与接口参数为 `arrival_date`（不采用：需要库迁移与前后端契约同步，
  本期收益不足）；保留「销售日期」并新增说明（不采用：用户已明确要求统一叫到达日期）。
- Consequences：1) 文档与代码中仍保留 `sale_date` 等字段名，读代码时会看到「字段名 vs 界面名」不一致，
  以本 ADR 为准；2) 到港日期字段与库迁移仍在 `docs/TODO.md` 中，未来若新增真正的到港字段需另行区分。
- Revision（2026-09-10）：原文「接口参数仍为 `sale_date_start` / `sale_date_end`」与实现不符，
  实际 API 参数为 `start_date` / `end_date`；本次修正为本条目实际契约，不改变接口行为。

## ADR-011 — 对比页 AI 分析结论接入大模型（按需生成 + 缓存）

- Date：2026-09-10
- Status：Accepted
- Context：用户要求在对比页直接给结论（「对比的页面还需要有一个 ai 分析的功能」），
  目标用户是果农与档口老板，不愿自己读表；仓库根 `.env` 已配置
  `FRUIT_ANALYSIS_AI_API_KEY` / `FRUIT_ANALYSIS_AI_BASE_URL` / `FRUIT_ANALYSIS_AI_MODEL`，
  但此前全仓库无任何引用（见 HANDOFF Known Issues 1）。
- Decision：
  1. 新增 `POST /api/analytics/series-comparison/analysis`，本期只服务「系列对比」页；
     结算单对比页后续复用同一接口。
  2. 结论只依据后端已算好的聚合数字：提示词明确「不许编造、不许自己另算、不得改口径」，
     并按固定 5 个小标题（整体行情 / A果 / B果 / C果 / 可以留意的地方）输出。
  3. 模型配置只从进程环境变量与仓库根 `.env` 读取；缺少 API Key 时返回 503 与中文提示，
     不影响页面其它功能。密钥不写入代码、不返回前端、不落日志。
  4. 调用用标准库 `urllib` 走 OpenAI 兼容的 `/chat/completions`，**不新增第三方依赖**。
  5. 结论按「功能 + 提示词版本 + 勾选结算单 + 到达日期范围」哈希缓存到新表 `ai_analysis`；
     `refresh=true` 时重新生成，其余情况直接返回缓存。
  6. 关闭模型「思考」（`reasoning_effort: none`）；服务商不认该参数时自动去掉重试。
- Why：1) 果农看不懂表格，需要一句人话结论；2) 大模型调用慢且收费，缓存避免重复付费；
  3) 前端直连会把密钥暴露给浏览器，必须由后端代发；4) 实测推理型模型（`deepseek-v4-flash`）
  关闭思考前单次思考可达 8000 token，正文常被截断，关闭后 2~3 秒返回且稳定。
- Alternatives：前端直连大模型（不采用：密钥进浏览器）；引入 `openai` SDK（不采用：标准库够用，
  且仓库规则要求不随意新增依赖）；每天定时批量生成（不采用：数据随时变化，按需生成更省）。
- Consequences：1) 结论仅供参考，页面显著标注「请以表格数字为准」；2) 输出质量依赖提示词，
  修改提示词需同时提升 `PROMPT_VERSION`，否则会读到旧结论；3) `ai_analysis` 表随
  `init_db()` 自动创建，无需额外迁移脚本；4) 单次失败给出中文提示并允许「重新生成」。

## ADR-012 — 清关费以清关单为准，清关单没有即为没有

- Date：2026-09-11
- Status：Accepted
- Context：线上 4 张结算单中，单 640 的 `settlement_summary.customs_tax` 为空，
  导致其应付金额（384,740 元）明显高于其他结算单。此前在走查中曾被记为「疑似缺失」。
- Decision：清关费一律以清关单数据为准；**清关单没有清关费记录，即视为该结算单没有清关费**，
  不补值、不推算、不按其他结算单均值填充。
- Why：1) 业务上清关费来自独立的清关单，与结算单不是同源数据；2) 统一口径可避免
  系统擅自「补算」出与清关单不一致的数字；3) 空值本身是有效业务事实，不应被当作错误。
- Alternatives：按其他结算单均值填充（不采用：等于编造数据）；缺失即报错拦截导入
  （不采用：会把正常业务判为失败）。
- Consequences：1) 单 640 的应付 384,740 元为真实值，不做数据修正；
  2) 跨结算单比较「每件应付」时需意识到清关费口径差异，界面不得暗示该单数据异常；
  3) 导入时**不因清关费为空而生成 `data_issue`**。

## ADR-013 — 「等级细分」作为下一阶段主线

- Date：2026-09-11
- Status：Accepted
- Context：全系统走查发现 `sale_record.grade_raw` 已保留 35 种原始等级写法
  （含号别 5/6/7/8/9、箱重 17/19/19.5KG、品质后缀 熟/裂/黄皮），但分析链路只使用
  A/B/C 三档，信息量被大幅压缩。业务方确认下一阶段优先做等级细分。
- Decision：1) 下一阶段主线为**等级细分**，从 `grade_raw` 派生出更细的等级标签用于分析；
  2) **不改变** ADR-002 的 A/B/C 主口径与 `grade` 字段，细分是叠加维度，不是替换；
  3) 细分只在服务层派生，**不新增数据库列、不做库迁移**；4) 具体号别分桶规则
  （含 `B6/7` 这类区间的归属）在实施前单独确认。
- Why：1) 零新增数据依赖，信息已在库中；2) 实测 A6 均价约 558 元/件、`A5熟` 约 430 元/件，
  说明细分的价格差异显著，对果农有直接决策价值；3) 服务层派生可回滚、可快速迭代。
- Alternatives：新增 `grade_detail` 列落库（不采用：本期无查询性能压力，且会引入迁移成本）；
  在导入时改写 `grade`（不采用：破坏 ADR-002 主口径与历史可比性）。
- Consequences：1) 细分标签由解析规则决定，规则变更需提升版本并复核历史结果；
  2) 无法识别的写法需归入「其他」并在数据质量看板暴露，不得静默丢弃；
  3) 前端新增细分对比视图，A/B/C 三档视图保持不变。

### ADR-013 Revision（2026-09-11）

- 分桶规则已确认：采用**方案 A**——单号各自成桶（`A5`、`A6`），区间保留原样成桶（`B6/7`、`C6/8`、
  `BC5/7/8`），品质后缀（熟/裂/黄皮）不参与分桶。
- 依据：方案 A 件数合计与实际总量一致（3,821 件）；方案 B 会重复计入导致虚高（4,874 件）；
  方案 C 会把 `B7/5` 记为 B5，低估大号价值。
- 品质后缀处理已确认：**只做标记**（在号别行上显示熟/裂/黄皮），不单独统计、不参与分桶。
- 入口已确认：**不新增一级菜单**，做进「系列对比」页的视图切换（按系列 ↔ 按等级号别）。
- 果类已确认：**后续可能会有其他水果**，因此解析规则按果类可插拔
  （`register_fruit_grade_parser`），聚合键为「果类 + 标签」；当前只有榴莲，不做果类分组。
- AI 小结已确认：**本次一起做**，新增 `POST /api/analytics/grade-detail/analysis`，
  复用 ADR-011 的缓存与调用机制，`feature='grade-detail'`、口径版本 `v1-schemeA`；
  数据包必须带样本量，样本少于 5 张结算单时提示词禁止输出趋势类结论。

## ADR-014 — AI 结论改为「后端先算对比、模型只做解读」

- Date：2026-09-11
- Status：Accepted
- Context：线上实测两类 AI 结论都只把数字重述一遍（「可以留意的地方」写的是
  「B 级件数最多」这种复述），对果农没有决策价值；同时结论区与普通表格视觉上无差别，
  用户反馈「显示的内容要明显一点」「分析尽可能往深处挖」。
- Decision：
  1) **对比信号全部由后端预计算**，随数据包一起给模型：结算单价差排名与极值差、
     等级结构信号（金额占比减件数占比）、号别价格排名、同级号别价差、同号别跨结算单价差、
     品质标记对比、大等级汇总。模型只允许引用，不允许自己加总或重算。
  2) **提示词升级为「结论 + 比较 + 建议」**：「可以留意的地方」必须给出 2 到 3 条
     能直接照做的动作（分选、提价、复盘、写法规范），并明确禁止「继续关注」这类空话。
  3) **提示词或数据包变化必须提升 `PROMPT_VERSION`**：系列对比 `v1 → v2`，
     等级细分 `v1-schemeA → v3-schemeA`，旧缓存自动失效。
  4) 前端 AI 结论区改为**主色强调卡片 + 关键数字高亮 + 建议小节暖色底**，
     与普通数字表格在视觉上区分开。
- Why：1) 大模型对「多步聚合」不可靠——实测让它自己加总 C 级各号别占比，得到 22.7%，
  真实值是 25.1%；把聚合放到后端并显式提供「大等级汇总」后结果正确。
  2) 模型擅长的是组织语言与归因，不是算术；把计算和表达分开，结论才既准又深。
- Alternatives：加大模型输出长度（不采用：长不等于深，仍是复述）；
  让模型自己算差值（不采用：已实测会算错，且无法追溯）。
- Consequences：1) 单次调用的输入 token 变多（等级细分数据包约 6k 字符），
  但结论可直接被果农使用；2) 新增或调整指标时必须同步扩展 `insights`，
  否则模型缺少对比字段会退回复述；3) 结论只覆盖数据包里的字段，
  不能回答「为什么这批货便宜」这类需要外部信息的问题。

## ADR-015 — 单号双写：原始单号 + 适配后单号，页面统一展示适配后单号

- Date：2026-09-11
- Status：Accepted
- Context：填写人员文化程度有限，单号写法不统一（线上 4 单为
  `宝贝01` / `宝贝02` / `宝贝003` / `宝贝L004`），页面各处各自展示原始写法，
  果农难以把它们认成同一套编号；同时业务方要求原始写法必须可追溯，不能改写或丢弃。
- Decision：
  1) `import_batch` 增加 `order_no_normalized` 列，**原始单号 `order_no` 保持原
     入库写法**，两个字段同时落库；
  2) 统一命名规则集中在 `backend/app/services/order_no_naming.py`：全角转半角（NFKC）→
     取开头连续中文为系列名 → 去掉 `-`/空格/`_`/`·` 等分隔符、字母转大写 →
     序号为「字母+数字」时数字左补零到 3 位 → 输出 `系列-序号`
     （`宝贝003` → `宝贝-003`、`宝贝01` → `宝贝-001`、`宝贝L004` → `宝贝-L004`）；
  3) **识别不出中文系列时不做改写**，原样返回（如 `626`），避免把未知写法改坏；
  4) 页面统一展示适配后单号；原始单号保留在接口字段中，以 tooltip / 副标题呈现，
     便于追溯填写人员的写法；
  5) 查询层（`order_no_display`）在适配后单号为空时按同一规则实时派生，
     兼容尚未回填的历史数据与只写了 `order_no` 的测试夹具。
- Why：1) 页面统一命名才能让果农把同一系列的多张单认成一套；
  2) 原始写法是追责与复核依据，改写会丢信息，因此必须双写而不是就地覆盖；
  3) 规则放在服务层纯函数里，规则调整只需改一处并可回填重算（`--force`）。
- Alternatives：只在前端做展示转换（不采用：导出、AI 数据包、导入记录等非前端出口
  仍会露出原始写法，无法“全站统一”）；直接把 `order_no` 改成统一写法
  （不采用：丢失原始信息，且违反业务方可追溯要求）。
- Consequences：1) 新增一列与一次迁移（`backend/scripts/add_order_no_normalized.py`，
   幂等、默认演练、带 SQL 快照、支持 `--force` 重算）；
   2) 序号补零只是展示口径，**不改变单号语义**，`宝贝01` 与 `宝贝1` 会归一到同一显示名，
   属于预期行为；3) AI 数据包改为「单号=适配后、原始单号=原样」，
   系列对比 `PROMPT_VERSION` 由 `v2` 提升到 `v3`，旧缓存自动失效；
   4) 新增单号相关展示位时必须走 `order_no_normalized`，不得直接展示 `order_no`。

## ADR-016 — 商号双写：原始商号 + 适配后商号，页面统一展示适配后商号

- Date：2026-09-11
- Status：Accepted
- Context：商号写法不统一（线上 4 单为 `单637` / `单624` / `626` / `640`），
  填写人员习惯在部分商号前多加一个「单」字；但商号同时是结算单的业务唯一键、
  接口参数、前端下拉取值与地址栏 `selected=` 的值，**不能改值**，否则会破坏唯一键、
  已有分享链接与接口契约；而页面又需要统一展示口径。
- Decision：
  1) `import_batch` 增加 `merchant_no_normalized` 列，**原始商号 `merchant_no` 保持原
     入库写法**，两个字段同时落库；
  2) 统一规则集中在 `backend/app/services/merchant_no_naming.py`：全角转半角（NFKC）→
     去掉所有空白 → 去掉开头「单」前缀（可重复）→ 字母转大写
     （`单637` → `637`、`单624` → `624`、`626` / `640` 不变）；
  3) 去掉「单」后为空时**原样返回**，避免把纯「单」这种写法改坏；
  4) **`merchant_no` 仍是业务唯一键、接口参数、前端下拉取值与地址栏 `selected=` 的值**，
     只有展示走 `merchant_no_normalized`，实现「展示统一但不改契约」；
  5) 查询层（`merchant_no_display`）在适配后商号为空时按同一规则实时派生，
     兼容尚未回填的历史数据与只写了 `merchant_no` 的测试夹具。
- Why：1) 商号是唯一键性质的值，就地改写会同时破坏唯一键、接口契约与已分享链接；
  2) 双写能在不改契约的前提下统一页面口径，并保留原始写法可追溯；
  3) 规则放在服务层纯函数里，调整只需改一处并可回填重算（`--force`）。
- Alternatives：直接把 `merchant_no` 改成去「单」写法（不采用：破坏唯一键 / 接口参数 /
  已分享链接，且丢失原始写法）；只在前端做展示转换（不采用：导出、AI 数据包、
  导入记录等非前端出口仍会露出原始写法，无法“全站统一”）。
- Consequences：1) 新增一列与一次迁移（`backend/scripts/add_merchant_no_normalized.py`，
   复用通用工具 `backend/scripts/column_backfill.py`，幂等、默认演练、带 SQL 快照、
   支持 `--force` 重算）；2)「最高价商号 / 最低价商号」等分析文案改用适配后商号；
   3) 导出 xlsx 元数据与文件名使用适配后商号（同时保留原始商号），
   AI 系列数据包 `PROMPT_VERSION` 由 `v3` 提升到 `v4`，旧缓存自动失效；
   4) 新增商号展示位时必须走 `merchant_no_normalized`，不得直接渲染 `merchant_no`。
