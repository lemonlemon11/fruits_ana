## ADR-001 — 使用 MySQL 作为唯一业务库

- Date：2026-09-09
- Status：Accepted
- Context：原型阶段以 SQLite 文件 + CSV 产物验证口径；正式系统需要并发访问、事务与
  多端共享数据。
- Decision：业务数据统一存 MySQL，应用通过 SQLAlchemy 2.0 + PyMySQL 访问。
- Why：1) 需要事务与并发写入；2) 需要长期运行的服务端存储；3) 已有 SQLite → MySQL
  迁移工具可平滑过渡。
- Alternatives：继续使用 SQLite（不采用：并发与部署形态不满足）；CSV/Excel 作为主存储
  （不采用：无法支撑查询与一致性）。
- Consequences：优点是可部署为服务并支持多人使用；缺点是引入了数据库运维与迁移成本，
  schema 变更必须配套可重复执行的迁移脚本。迁移工具见 `backend/scripts/migrate_sqlite_to_mysql.py`。

## ADR-002 — BC 等级归入 C 级

- Date：2026-09-08
- Status：Superseded by ADR-029（2026-09-17）
- Context：结算单品种规格存在 A / B / C / BC 四种等级标识，报表需要统一分级。
- Decision：`BC` 归入 `C`，界面显示为「C 果（含 BC）」。
- Why：历史报表标题「C 果（C/BC 级）」佐证口径一致。
- Consequences：导入后 `sale_record` 不再保留 BC 独立等级；展示文案需保持一致。

## ADR-003 — 第一期不做利润测算

- Date：2026-09-08
- Status：Accepted
- Context：最终目标包含利润测算，但当前没有采购成本与国内物流/报关费用数据。
- Decision：第一期只做存量销售数据的存档、导入与可视化；利润测算留待第二期，且必须先确认
  成本数据口径。
- Consequences：数据模型需为后续成本维度留出扩展空间，但不得凭空臆测字段结构。

## ADR-004 — 数据接入方式为整批文件上传

- Date：2026-09-08
- Status：Accepted
- Decision：用户维护 Excel/CSV 文件，通过 `/api/imports` 整批上传；暂不做粘贴文本解析或逐条表单录入。
- Consequences：解析器需兼容多种结算单版式（柜号在表头上方、日期合并、等级写在品种规格中）。

## ADR-005 — 认证采用服务端会话 + HttpOnly Cookie

- Date：2026-09-09
- Status：Accepted
- Context：需要登录才能访问业务页，但系统为单体应用、无第三方 OAuth 需求。
- Decision：使用 Argon2 哈希密码；登录后创建服务端会话，数据库只保存 token 的 SHA-256 哈希，
  浏览器通过 HttpOnly Cookie `fruit_session` 携带凭证，有效期 7 天。
- Why：1) 会话可服务端撤销（登出/失效）；2) Cookie 无法被前端 JS 读取，降低 XSS 窃取风险；
  3) 无需引入 JWT 签名密钥与刷新令牌机制。
- Alternatives：JWT（不采用：撤销成本高、需要额外密钥管理）；前端 localStorage 存 token
  （不采用：XSS 风险更高）。
- Consequences：水平扩展时需要共享会话存储；跨域部署需调整 Cookie 策略。

## ADR-006 — 指标口径以「金额 ÷ 数量」为准

- Date：2026-09-09
- Status：Accepted
- Decision：销售数量取 `quantity` 之和；销售金额取 `amount` 之和；加权均价 = 销售金额 / 销售数量，
  数量为 0 时返回空值；数量占比 = 某等级数量 / 同筛选范围总数量；日期筛选按销售日期计算。
- Consequences：所有新增报表必须复用同一口径，禁止在视图层重新定义平均值。

## ADR-007 — 前端不引入图表库与 UI 组件库

- Date：2026-09-09
- Status：Accepted
- Context：图表形态固定（趋势线、占比饼图、对比柱状），且需要适配移动端与换肤。
- Decision：图表以手写 SVG 组件实现，样式使用项目内 CSS 变量与 `styles-*.css`。
- Why：避免额外依赖体积与样式冲突，便于精确控制移动端布局与主题变量。
- Consequences：新增图表需要自行实现，改动时注意移动端断点与主题变量一致性。

## ADR-008 — 以「商号」作为结算单业务唯一键

- Date：2026-09-10
- Status：Accepted
- Context：柜号不唯一（637 与 640 两张结算单共用柜号 CBHU2970762），单号为客户侧编号且可能重复，
  仅用柜号会导致分析口径混淆；商号是我司记录的商业合同唯一单据号。
- Decision：`import_batch` 承担结算单职责并持有唯一业务键 `merchant_no`（商号），
  同时保存 `order_no`（单号）、`container_no`（柜号，可为空）、`vehicle_no`（转运车号）；
  分析、导出、前端全部以商号作为查询与归集维度，`sale_record` 不再保存柜号。
  同一商号再次导入默认返回 `conflict`，用户确认后以覆盖方式替换整张结算单。
- 界面约定：下拉框按**「商号（单号）」**展示（如 `商号 640（宝贝L004）`），取值仍为商号（唯一键）。
  2026-09-10 客户再次确认「商号才是唯一的，单号也近似唯一但存在重复」后，展示顺序由
  「单号（商号）」调整为商号在前，避免重复柜号或重复单号造成误选；
  筛选字段名与占位文案同步由「单号 / 选择单号」改为「商号 / 选择商号」
  （表格里的「单号」列仍指单号本身，不受影响）。
- Why：1) 商号来自我司合同，业务上唯一且可追溯；2) 柜号可能缺失或重复，不适合做身份；
  3) 覆盖式导入保证「一张商号 = 一份最新结算单」，避免同一张单据出现多份明细。
- Alternatives：以单号 `settlement_no` 作唯一键（不采用：单号为客户侧编号，规则上允许重复）；
  以柜号作唯一键（不采用：已证明重复且可能缺失）。
- 依据文档：`docs/superpowers/specs/2026-09-10-merchant-number-dimension-design.md`、
  `docs/superpowers/plans/2026-09-10-merchant-number-dimension.md`；
  早期「单号唯一键」方案（`2026-09-10-settlement-number-identity-*`）已被本条目取代。
- Consequences：`sale_record.container_id/container_name`、`container_summary` 表已废弃，
  线上库需执行 `backend/scripts/backfill_settlement_identity.py` 完成表结构迁移与商号回填（含 SQL 快照）。

## ADR-009 — 系列从单号中文前缀识别，对比口径为「元/件」

- Date：2026-09-10
- Status：Accepted
- Context：「系列对比」需要把结算单归到系列（如 `宝贝01`、`宝贝02`、`宝贝003`、`宝贝L004` 同属「宝贝」），
  但结算单里没有独立的系列字段；同时各系列箱重不同（宝贝为 17 / 19 / 19.5KG 混装），
  跨系列用「元/件」还是「元/KG」需要拍板。
- Decision：
  1. 系列由结算单**单号**（`order_no`）开头连续的中文前缀推导；识别不出时归入「未识别系列」，不阻塞对比。
  2. 对比主体是结算单（商号唯一键），系列仅作分组与汇总；用户按业务单勾选，支持同系列内和跨系列对比。
  3. 均价口径统一为「销售金额 ÷ 件数」（元/件），与全站口径一致；本期不做元/KG 换算。
  4. 一次最多勾选 6 张结算单（前端限制），保证图表可读。
- Why：1) 单号是现有数据中唯一能稳定体现系列归属的字段；2) 用户明确选择元/件口径；
  3) 不新增字段、不改库，可立即上线，后续再考虑维护系列别名字典。
- Alternatives：新增 `brand` 表与人工维护别名（不采用：需要额外维护成本与一次迁移，本期无必要）；
  从文件名识别系列（不采用：文件名可随意修改，不可靠）；元/KG 口径（不采用：需要新增重量解析与回填，
  且用户已确认元/件）。
- Consequences：
  1. 单号命名不规范（如 `626`）会落入「未识别系列」，需要在导入时人工确认单号。
  2. 空值/异常写入不会抛错，但系列名可能不等于业务预期品牌名。
  3. 元/KG 对比、AI 分析结论、Excel 导出不在本期范围，见 `docs/TODO.md`。
- 依据文档：`docs/superpowers/specs/2026-09-10-brand-series-analysis-design.md`（含本次修订段落）。

> 修订（2026-09-13）：按用户要求，仅将全站展示文案从「平均每件售价 / 元每件」调整为
> 「平均每千克售价 / 元每千克」；计算字段与公式不变，仍为 `销售金额 ÷ 销量`，本期不做元/KG 换算。
>
> 修订（2026-09-18）：用户确认恢复为「平均每件售价 / 元/件 / 销量（件）」；全站页面、图表、
> 导出、AI 数据包与问答提示词同步调整。计算字段与公式仍不变：`销售金额 ÷ 数量`，数量即件数。
>
> 修订（2026-09-20）：按用户要求，全站用户可见文案将「平均每件售价」统一改为「每件均价」；
> 计算字段与公式不变：`每件均价 = 销售金额 ÷ 销量（件）`。前端页面、导出表头、AI 提示词
> 与数据包同步调整，并提升对应 `PROMPT_VERSION` 使旧缓存失效。

## ADR-010 — 界面日期统一显示为「到达日期」

- Date：2026-09-10
- Status：Accepted
- Context：用户口述口径为「日期统一叫到达日期就行」。此前界面同一字段存在
  「销售日期」「首销日期」「日期」「销售周期」多种叫法，且筛选控件写作「开始日期 / 结束日期」，
  同一页里出现多种叫法，用户难以判断查的是哪一天。
- Decision：结算单日期在**界面上一律显示为「到达日期」**，具体包括
  表头（结算单列表 / 结算单明细 / 数据明细 / 趋势表 / 系列总览）、筛选控件
  （统一为「到达日期起」「到达日期止」）、区间说明与空状态文案（如「到达日期：8/27 至 9/05」）。
  数据层不变：数据库字段仍为 `sale_record.sale_date`，接口参数仍为 `start_date` / `end_date`，
  解析仍按源表 `销售日期 / 日期 / 销售时间` 表头识别。
- Why：1) 该日期在业务上就是货物到达日期，用户以此对账；2) 同一字段多种叫法会让果农误判；
  3) 只改文案不改字段，零迁移、零接口变更，风险最低。
- Alternatives：改库字段名与接口参数为 `arrival_date`（不采用：需要库迁移与前后端契约同步，
  本期收益不足）；保留「销售日期」并新增说明（不采用：用户已明确要求统一叫到达日期）。
- Consequences：1) 文档与代码中仍保留 `sale_date` 等字段名，读代码时会看到「字段名 vs 界面名」不一致，
  以本 ADR 为准；2) 到港日期字段与库迁移仍在 `docs/TODO.md` 中，未来若新增真正的到港字段需另行区分。
- Revision（2026-09-10）：原文「接口参数仍为 `sale_date_start` / `sale_date_end`」与实现不符，
  实际 API 参数为 `start_date` / `end_date`；本次修正为本条目实际契约，不改变接口行为。

## ADR-011 — 对比页 AI 分析结论接入大模型（按需生成 + 缓存）

- Date：2026-09-10
- Status：Accepted
- Context：用户要求在对比页直接给结论（「对比的页面还需要有一个 ai 分析的功能」），
  目标用户是果农与档口老板，不愿自己读表；仓库根 `.env` 已配置
  `FRUIT_ANALYSIS_AI_API_KEY` / `FRUIT_ANALYSIS_AI_BASE_URL` / `FRUIT_ANALYSIS_AI_MODEL`，
  但此前全仓库无任何引用（见 HANDOFF Known Issues 1）。
- Decision：
  1. 新增 `POST /api/analytics/series-comparison/analysis`，本期只服务「系列对比」页；
     结算单对比页后续复用同一接口。
  2. 结论只依据后端已算好的聚合数字：提示词明确「不许编造、不许自己另算、不得改口径」，
     并按固定 5 个小标题（整体行情 / A果 / B果 / C果 / 可以留意的地方）输出。
  3. 模型配置只从进程环境变量与仓库根 `.env` 读取；缺少 API Key 时返回 503 与中文提示，
     不影响页面其它功能。密钥不写入代码、不返回前端、不落日志。
  4. 调用用标准库 `urllib` 走 OpenAI 兼容的 `/chat/completions`，**不新增第三方依赖**。
  5. 结论按「功能 + 提示词版本 + 勾选结算单 + 到达日期范围」哈希缓存到新表 `ai_analysis`；
     `refresh=true` 时重新生成，其余情况直接返回缓存。
  6. 关闭模型「思考」（`reasoning_effort: none`）；服务商不认该参数时自动去掉重试。
- Why：1) 果农看不懂表格，需要一句人话结论；2) 大模型调用慢且收费，缓存避免重复付费；
  3) 前端直连会把密钥暴露给浏览器，必须由后端代发；4) 实测推理型模型（`deepseek-v4-flash`）
  关闭思考前单次思考可达 8000 token，正文常被截断，关闭后 2~3 秒返回且稳定。
- Alternatives：前端直连大模型（不采用：密钥进浏览器）；引入 `openai` SDK（不采用：标准库够用，
  且仓库规则要求不随意新增依赖）；每天定时批量生成（不采用：数据随时变化，按需生成更省）。
- Consequences：1) 结论仅供参考，页面显著标注「请以表格数字为准」；2) 输出质量依赖提示词，
  修改提示词需同时提升 `PROMPT_VERSION`，否则会读到旧结论；3) `ai_analysis` 表随
  `init_db()` 自动创建，无需额外迁移脚本；4) 单次失败给出中文提示并允许「重新生成」。

## ADR-012 — 清关费以清关单为准，清关单没有即为没有

- Date：2026-09-11
- Status：Accepted
- Context：线上 4 张结算单中，单 640 的 `settlement_summary.customs_tax` 为空，
  导致其应付金额（384,740 元）明显高于其他结算单。此前在走查中曾被记为「疑似缺失」。
- Decision：清关费一律以清关单数据为准；**清关单没有清关费记录，即视为该结算单没有清关费**，
  不补值、不推算、不按其他结算单均值填充。
- Why：1) 业务上清关费来自独立的清关单，与结算单不是同源数据；2) 统一口径可避免
  系统擅自「补算」出与清关单不一致的数字；3) 空值本身是有效业务事实，不应被当作错误。
- Alternatives：按其他结算单均值填充（不采用：等于编造数据）；缺失即报错拦截导入
  （不采用：会把正常业务判为失败）。
- Consequences：1) 单 640 的应付 384,740 元为真实值，不做数据修正；
  2) 跨结算单比较「每件应付」时需意识到清关费口径差异，界面不得暗示该单数据异常；
  3) 导入时**不因清关费为空而生成 `data_issue`**。

## ADR-013 — 「等级细分」作为下一阶段主线

- Date：2026-09-11
- Status：Accepted
- Context：全系统走查发现 `sale_record.grade_raw` 已保留 35 种原始等级写法
  （含号别 5/6/7/8/9、箱重 17/19/19.5KG、品质后缀 熟/裂/黄皮），但分析链路只使用
  A/B/C 三档，信息量被大幅压缩。业务方确认下一阶段优先做等级细分。
- Decision：1) 下一阶段主线为**等级细分**，从 `grade_raw` 派生出更细的等级标签用于分析；
  2) **不改变** ADR-002 的 A/B/C 主口径与 `grade` 字段，细分是叠加维度，不是替换；
  3) 细分只在服务层派生，**不新增数据库列、不做库迁移**；4) 具体号别分桶规则
  （含 `B6/7` 这类区间的归属）在实施前单独确认。
- Why：1) 零新增数据依赖，信息已在库中；2) 实测 A6 均价约 558 元/件、`A5熟` 约 430 元/件，
  说明细分的价格差异显著，对果农有直接决策价值；3) 服务层派生可回滚、可快速迭代。
- Alternatives：新增 `grade_detail` 列落库（不采用：本期无查询性能压力，且会引入迁移成本）；
  在导入时改写 `grade`（不采用：破坏 ADR-002 主口径与历史可比性）。
- Consequences：1) 细分标签由解析规则决定，规则变更需提升版本并复核历史结果；
  2) 无法识别的写法需归入「其他」并在数据质量看板暴露，不得静默丢弃；
  3) 前端新增细分对比视图，A/B/C 三档视图保持不变。

  （`register_fruit_grade_parser`），聚合键为「果类 + 标签」；当前只有榴莲，不做果类分组。
- AI 小结已确认：**本次一起做**，新增 `POST /api/analytics/grade-detail/analysis`，
  复用 ADR-011 的缓存与调用机制，`feature='grade-detail'`、口径版本 `v1-schemeA`；
  数据包必须带样本量，样本少于 5 张结算单时提示词禁止输出趋势类结论。

## ADR-014 — AI 结论改为「后端先算对比、模型只做解读」

- Date：2026-09-11
- Status：Accepted
- Context：线上实测两类 AI 结论都只把数字重述一遍（「可以留意的地方」写的是
  「B 级件数最多」这种复述），对果农没有决策价值；同时结论区与普通表格视觉上无差别，
  用户反馈「显示的内容要明显一点」「分析尽可能往深处挖」。
- Decision：
  1) **对比信号全部由后端预计算**，随数据包一起给模型：结算单价差排名与极值差、
     等级结构信号（金额占比减件数占比）、号别价格排名、同级号别价差、同号别跨结算单价差、
     品质标记对比、大等级汇总。模型只允许引用，不允许自己加总或重算。
  2) **提示词升级为「结论 + 比较 + 建议」**：「可以留意的地方」必须给出 2 到 3 条
     能直接照做的动作（分选、提价、复盘、写法规范），并明确禁止「继续关注」这类空话。
  3) **提示词或数据包变化必须提升 `PROMPT_VERSION`**：系列对比 `v1 → v2`，
     等级细分 `v1-schemeA → v3-schemeA`，旧缓存自动失效。
  4) 前端 AI 结论区改为**主色强调卡片 + 关键数字高亮 + 建议小节暖色底**，
     与普通数字表格在视觉上区分开。
- Why：1) 大模型对「多步聚合」不可靠——实测让它自己加总 C 级各号别占比，得到 22.7%，
  真实值是 25.1%；把聚合放到后端并显式提供「大等级汇总」后结果正确。
  2) 模型擅长的是组织语言与归因，不是算术；把计算和表达分开，结论才既准又深。
- Alternatives：加大模型输出长度（不采用：长不等于深，仍是复述）；
  让模型自己算差值（不采用：已实测会算错，且无法追溯）。
- Consequences：1) 单次调用的输入 token 变多（等级细分数据包约 6k 字符），
  但结论可直接被果农使用；2) 新增或调整指标时必须同步扩展 `insights`，
  否则模型缺少对比字段会退回复述；3) 结论只覆盖数据包里的字段，
  不能回答「为什么这批货便宜」这类需要外部信息的问题。

## ADR-015 — 单号双写：原始单号 + 适配后单号，页面统一展示适配后单号

- Date：2026-09-11
- Status：Accepted
- Context：填写人员文化程度有限，单号写法不统一（线上 4 单为
  `宝贝01` / `宝贝02` / `宝贝003` / `宝贝L004`），页面各处各自展示原始写法，
  果农难以把它们认成同一套编号；同时业务方要求原始写法必须可追溯，不能改写或丢弃。
- Decision：
  1) `import_batch` 增加 `order_no_normalized` 列，**原始单号 `order_no` 保持原
     入库写法**，两个字段同时落库；
  2) 统一命名规则集中在 `backend/app/services/order_no_naming.py`：全角转半角（NFKC）→
     取开头连续中文为系列名 → 去掉 `-`/空格/`_`/`·` 等分隔符、字母转大写 →
     序号只保留数字（字母标记不进编号）并左补零到 3 位 → 输出 `系列-序号`
     （`宝贝003` → `宝贝-003`、`宝贝01` → `宝贝-001`、`宝贝L004` → `宝贝-004`）；
  3) **识别不出中文系列时不做改写**，原样返回（如 `626`），避免把未知写法改坏；
  4) 页面统一展示适配后单号；原始单号保留在接口字段中，以 tooltip / 副标题呈现，
     便于追溯填写人员的写法；
  5) 查询层（`order_no_display`）在适配后单号为空时按同一规则实时派生，
     兼容尚未回填的历史数据与只写了 `order_no` 的测试夹具。
- Why：1) 页面统一命名才能让果农把同一系列的多张单认成一套；
  2) 原始写法是追责与复核依据，改写会丢信息，因此必须双写而不是就地覆盖；
  3) 规则放在服务层纯函数里，规则调整只需改一处并可回填重算（`--force`）。
- Alternatives：只在前端做展示转换（不采用：导出、AI 数据包、导入记录等非前端出口
  仍会露出原始写法，无法“全站统一”）；直接把 `order_no` 改成统一写法
  （不采用：丢失原始信息，且违反业务方可追溯要求）。
- Consequences：1) 新增一列与一次迁移（`backend/scripts/add_order_no_normalized.py`，
   幂等、默认演练、带 SQL 快照、支持 `--force` 重算）；
   2) 序号补零只是展示口径，**不改变单号语义**，`宝贝01` 与 `宝贝1` 会归一到同一显示名，
   属于预期行为；3) AI 数据包改为「单号=适配后、原始单号=原样」，
   系列对比 `PROMPT_VERSION` 由 `v2` 提升到 `v3`，旧缓存自动失效；
   4) 新增单号相关展示位时必须走 `order_no_normalized`，不得直接展示 `order_no`。
- 修订（2026-09-11，业务方反馈）：序号里的字母标记不再保留，`宝贝L004` 的 `L` 属于填写
  习惯、不是命名规范的一部分，适配后单号由 `宝贝-L004` 改为 `宝贝-004`
  （`_format_suffix` 只保留数字）。已用 `backend/scripts/add_order_no_normalized.py --force --apply`
  重算线上 4 行；系列对比 `PROMPT_VERSION` `v4 → v5`、等级细分 `v3-schemeA → v3-schemeA-2`，
  旧 AI 结论缓存自动失效（缓存的正文里可能仍写 `宝贝-L004`）。

## ADR-016 — 商号双写：原始商号 + 适配后商号，页面统一展示适配后商号

- Date：2026-09-11
- Status：Accepted
- Context：商号写法不统一（线上 4 单为 `单637` / `单624` / `626` / `640`），
  填写人员习惯在部分商号前多加一个「单」字；但商号同时是结算单的业务唯一键、
  接口参数、前端下拉取值与地址栏 `selected=` 的值，**不能改值**，否则会破坏唯一键、
  已有分享链接与接口契约；而页面又需要统一展示口径。
- Decision：
  1) `import_batch` 增加 `merchant_no_normalized` 列，**原始商号 `merchant_no` 保持原
     入库写法**，两个字段同时落库；
  2) 统一规则集中在 `backend/app/services/merchant_no_naming.py`：全角转半角（NFKC）→
     去掉所有空白 → 去掉开头「单」前缀（可重复）→ 字母转大写
     （`单637` → `637`、`单624` → `624`、`626` / `640` 不变）；
  3) 去掉「单」后为空时**原样返回**，避免把纯「单」这种写法改坏；
  4) **`merchant_no` 仍是业务唯一键、接口参数、前端下拉取值与地址栏 `selected=` 的值**，
     只有展示走 `merchant_no_normalized`，实现「展示统一但不改契约」；
  5) 查询层（`merchant_no_display`）在适配后商号为空时按同一规则实时派生，
     兼容尚未回填的历史数据与只写了 `merchant_no` 的测试夹具。
- Why：1) 商号是唯一键性质的值，就地改写会同时破坏唯一键、接口契约与已分享链接；
  2) 双写能在不改契约的前提下统一页面口径，并保留原始写法可追溯；
  3) 规则放在服务层纯函数里，调整只需改一处并可回填重算（`--force`）。
- Alternatives：直接把 `merchant_no` 改成去「单」写法（不采用：破坏唯一键 / 接口参数 /
  已分享链接，且丢失原始写法）；只在前端做展示转换（不采用：导出、AI 数据包、
  导入记录等非前端出口仍会露出原始写法，无法“全站统一”）。
- Consequences：1) 新增一列与一次迁移（`backend/scripts/add_merchant_no_normalized.py`，
   复用通用工具 `backend/scripts/column_backfill.py`，幂等、默认演练、带 SQL 快照、
   支持 `--force` 重算）；2)「最高价商号 / 最低价商号」等分析文案改用适配后商号；
   3) 导出 xlsx 元数据与文件名使用适配后商号（同时保留原始商号），
   AI 系列数据包 `PROMPT_VERSION` 由 `v3` 提升到 `v4`，旧缓存自动失效；
   4) 新增商号展示位时必须走 `merchant_no_normalized`，不得直接渲染 `merchant_no`。

## ADR-017 — 登录会话支持可选 30 天免登录

- Date：2026-09-11
- Status：Accepted
- Context：ADR-005 将登录会话固定为 7 天，业务方希望用户可主动选择 30 天内免登录，
  同时要求该选项默认不勾选。
- Decision：
  1) `POST /api/auth/login` 请求新增向后兼容的 `remember_me: bool = false`；
  2) 未勾选时保持 ADR-005 的 7 天期限，勾选时服务端 `user_session.expires_at` 与
     HttpOnly Cookie `Max-Age` 同步改为 30 天；
  3) 注册自动创建的会话继续保持 7 天；前端不保存密码、不在 Web Storage 保存认证 token。
- Why：1) 延长期限必须同时约束服务端会话与 Cookie，否则两者会提前任一失效；
  2) 保留 7 天默认值可维持现有接口调用与安全边界；3) HttpOnly Cookie 延续 ADR-005 的
  XSS 风险控制，不为“记住登录”引入前端 token。
- Alternatives：所有用户统一改为 30 天（不采用：扩大默认认证窗口）；仅用前端记住用户名
  （不采用：不等于免登录）；把 token 存入 `localStorage`（不采用：增加 XSS 窃取风险）。
- Consequences：勾选用户的被盗会话有效窗口最长为 30 天，用户仍可通过退出登录立即撤销当前会话；
  后续如需“退出所有设备”，应基于现有 `user_session` 表批量撤销，不改变本 ADR。

  `sale_record.piece_count/spec_kg`、`settlement_after_sale_item`、`settlement_fee_item`、

     `admin_user_role` / 录单菜单）；`user` 表本身未受影响，账号与密码哈希保持原样。
  3) 恢复到 09-11 快照做逐字段校验（1244 个字段），差异只允许是**预期元数据差异**：
     导入时间 / 存储时间为重放时间、`user` / `user_session` 是快照更早的状态。
  4) 承认不可恢复的损失并留档：8 个文件的原始文件名、历史导入/存储时间戳、
     `ai_analysis` 缓存、`admin_notification` 通知、全部登录会话。
- Why：1) 业务数据全部是 Excel 派生的，原件尚在，重放是唯一可验证的恢复路径；
  2) 用快照逐字段比对能把「恢复是否正确」从口头保证变成可复现证据；
  3) 明确列出不可恢复项，避免把「看起来正常」当成「完全无损」。
- Alternatives：用 09-11 SQL 快照恢复（不采用：会丢掉 09-12 之后的 8 张结算单）；
  用 binlog 精确回放（不采用：缺少 `mysqlbinlog`、无 DB 主机访问，且 ROW 事件无法通过 SQL 解码）；
  断言「删表失败所以没事」（不采用：binlog 显示 12 条 DROP 已提交）。
- Consequences：1) 恢复后 12 张结算单 / 364 条销售明细 / 12 条摘要与快照口径一致，
  其中 `宝贝L004 → 宝贝-004` 的差异来自 09-11 之后的有意修复（`6aa0542`），非回归；
  2) 历史导入时间与原始文件名不可考，页面按「{商号}结算单（{单号}）.xlsx」展示推导名；
  3) 全体用户需重新登录；4) 后续必须补一条「非测试库禁止 destructive metadata 操作」的硬保护。

## ADR-022 — 同品牌经营分析的等级小标题只列当前结算单实际存在的等级

- Date：2026-09-15
- Status：Accepted
- Context：结算单详情的「同品牌经营分析」AI 卡片固定要求模型输出 9 个小标题
  （整体行情 + A-F + 其他 + 可以留意的地方），并要求「数据中没有的等级写暂无数据」，
  导致只有 A/B/C 的结算单也会渲染出「D果 / E果 / F果 / 其他」四个空小节
  （卡片里表现为标题 + 序号 1 + 「暂无数据」）。
- Decision：
  1) `settlement_ai_analysis_service` 的小标题清单改为**按当前结算单实际出现的等级动态生成**
     （`grade_headings` / `build_system_prompt`），只保留平台固定顺序中确实存在的等级；
  2) 删除提示词里「数据中没有的等级要写暂无数据」的要求，改为「没有的等级不要写，
     也不要写占位内容」；
  3) `PROMPT_VERSION` `v1 → v2`，让带空小节的旧结论缓存失效；
  4) 前端 `parseAnalysisSections` 丢弃纯「暂无数据」要点行 —— 小节因此不再出现，
     作为模型不听话时的兜底。
- Why：1) 空小节只占版面、不给信息，果农版要的是「这批货有什么就说什么」；
  2) 只在前端过滤会把缓存里的旧结构继续留在库里，必须在提示词层修正并失效缓存；
  3) 前端兜底成本极低，但能保证任何模型输出都不会再出现空小节。
- Alternatives：只改前端过滤（不采用：缓存里的旧结论结构不会被修正）；
  保留固定小标题但把空小节折叠（不采用：折叠仍占一次点击，业务方要的是不出现）；
  改成完全自由小标题（不采用：提示词与前端解析依赖固定标题做分节，稳定性更重要）。
- Consequences：1) 同品牌分析的输出小节数随结算单实际等级变化；2) 旧的
  `settlement-detail` AI 缓存自动失效一次，下次打开会重新生成；
  3) 品牌对比页（`ai_analysis_service`，`PROMPT_VERSION v7`）的固定小标题暂未调整，
  需业务确认后再决定是否同步。

## ADR-023 — 自然语言问答采用 Text-to-API，不让模型写 SQL 或重算指标

- Date：2026-09-15
- Status：Accepted（2026-09-15 已从 demo 整合进正式外壳）
- Context：客户提出「通过提问的方式搜索系统中的数据进行回答」。评估后确认可行，
  但若让大模型直接生成 SQL，会绕过后端既有的指标口径与数据访问边界，导致答案与看板
  不一致，也无法复用 ADR-014 的「后端先算、模型只解读」原则。
- Decision：
  1) 问答链路采用 **Text-to-API / function calling**：模型只负责理解问题、选择工具与组织措辞，
     数字一律来自 `ask_tools.py` 调用现有分析服务的结果。
  2) 工具目录只暴露 5 个只读能力：`list_settlements` / `get_overview` / `rank_settlements` /
     `get_settlement_detail` / `compare_settlements`；不提供任何 SQL 生成或写库工具。
  3) 提示词固化口径约束：数字必须能在工具结果中原样找到，禁止自行相加或重算；
     品牌或整组合计必须取 `compare_settlements` 的后端汇总；系统没有的字段直接拒绝编造。
  4) 问答接口为 `POST /api/ask`，鉴权走 `require_permission("ask:view")`；结果返回 `answer` / `steps` /
     `model`（`steps` 继续返回，供后续审计；正式界面按业务要求不展示溯源面板与模型名）。
  5) 权限收口（业务要求「只有 fruit_admin 才能看到」）：新增权限点 `ask:view`，
     仅在 `fruits_ana_admin` 的 `FRUIT_PERMISSIONS` 中登记、并只授予 `fruit_admin`；
     前端 `AppShell.vue` 用 `currentUser.permissions` 判断是否渲染 `AskWidget`。
- Why：1) 等级归并（BC→C）、金额÷数量、商号唯一键、同品牌对比、按销售日期筛选等口径是
  隐式契约，SQL 生成会破坏一致性；2) 工具层复用看板服务，口径升级只需跟随服务；
  3) 只读工具 + 参数校验 + 轮次上限，能显著降低越权查询、幻觉与空转风险。
- Alternatives：Text-to-SQL（不采用：口径与安全边界都不可控）；纯检索增强
  （不采用：数值类问题更需要结构化查询，而非文档召回）。
- Consequences：1) 2026-09-15 已整合进正式外壳：右下角悬浮机器人「顺仔」
  （`frontend/src/components/AskWidget.vue`）挂在 `AppShell.vue`，走 `/api/ask` 正式路由与
  `require_permission("ask:view")` 鉴权；`53001` 的 `dev-preview/ask-demo.html` 仅作历史留档；
  2) 新增 `ask_service` / `ask_tools` / `ask_payloads` / `ask_tool_schemas` 与 22 项后端测试、
  14 项前端测试；3) 权限已收口到 `ask:view`（只有 `fruit_admin` 持有，改角色授权即可扩权）；
  4) 未来若开放给客户，还需要补齐频控与调用审计。

## ADR-024 — 非测试库拒绝破坏性 DDL（ADR-021 事故的硬保护落地）

- Date：2026-09-15
- Status：Accepted
- Context：ADR-021 的根因是一条临时脚本直接 `import app.db` 拿到**真实库连接**后执行
  `Base.metadata.drop_all(bind=engine)`，删掉 12 张表。此前的隔离只靠 `tests/conftest.py`
  改环境变量，脚本与交互式调试完全绕得过去。事故留档时明确要求「后续必须补一条
  非测试库禁止 destructive metadata 操作的硬保护」，本次落地。
- Decision：
  1) 判定口径 `is_test_database(url)`：SQLite 一律视为测试库；非 SQLite 要求**库名含 `test`**；
  2) `Base` 改用 `GuardedMetaData`，重写 `drop_all`：非测试库直接抛 `RuntimeError`；
  3) 每个引擎挂 `before_cursor_execute` 监听器，裸 SQL 的
     `DROP TABLE / DROP DATABASE / DROP SCHEMA / TRUNCATE` 同样被拒
     （`ALTER TABLE ... DROP COLUMN` / `DROP INDEX` 不在拦截范围，以免挡住既有一次性迁移脚本）；
  4) 逃生口只保留一个：显式设置 `FRUIT_ANALYSIS_ALLOW_DESTRUCTIVE=1`，用于受控的一次性运维；
  5) `bind` 无法识别时按当前 `DATABASE_URL` 处理（fail-closed）；
  6) 业务端与管理端 `backend/app/db.py` 采用同一实现与同一环境变量名。
- Why：1) 拦截点选在「真正会删表的地方」，脚本、服务、REPL 都覆盖；
  2) 只认库名而不认环境变量，可让「连接串写错」这种最常见失误直接失败；
  3) 保留显式逃生口，避免把正常的建库/重建测试库流程彻底堵死。
- Alternatives：只在 `conftest.py` 里加强隔离（不采用：绕得过去，事故就是这么发生的）；
  只做代码评审约定（不采用：无强制力）；直接禁用 SQLAlchemy 的 `drop_all`（不采用：
  测试库重建与迁移工具需要它）。
- Consequences：1) 误触发时错误信息会打印脱敏连接串（不含口令）并指向 ADR-021；
  2) 新增 `backend/tests/test_db_guard.py` 6 项回归；3) 若将来需要删除生产表，
  必须显式带环境变量执行，并留下操作记录。

## ADR-025 — 文件导入与手工录单合并为一个菜单入口（选择方式页 + 本地草稿）

- Date：2026-09-15
- Status：Accepted
- Context：数据导入与手工录单是两条都要长期保留的录入链路。原侧栏只有一个「数据导入」入口，
  手工录单上线后若再加一项，果农版三入口导航会被撑到四项；同时业务方要求「手工单填到一半
  切走还能接着填」。视觉伴侣在 `53001` 出过 A/B/C 三套方案，业务确认采用方案 C。
- Decision：
  1) 侧栏第三项由「数据导入」改为「录单 / 导入」，指向新页面 `/entry-hub`；页面用
     「文件导入 / 手工录单」两张卡片选择录入方式，不把两条链路塞进同一个表单。
  2) `/imports`、`/entry` 两个既有路由与页签保持不变，`/entry-hub` 只做分流与回顾：
     列出最近 3 条导入批次（状态胶囊）与本地未完成的手工单（「继续录单」→ `/entry?draft=1`）。
  3) 菜单高亮由「单一前缀」改为「路径前缀 + `matches` 前缀集合」；`/entry-hub` 必须排在
     `/entry` 之前，否则页签命名会被 `/entry` 抢先匹配。
  4) 手工单草稿只存浏览器 `localStorage`（键 `fruit-entry-draft:v1:<userId>`），录入时防抖
     800ms 写入、保存成功后清除、组件卸载时冲刷；后端不新增草稿表。
  5) 无 `entry:view` 的角色在入口页只看到「文件导入」卡片与导入记录，不渲染草稿区块。
- Why：1) 两条链路都保留，用「选择方式」页分流比塞进一个选项卡页更少歧义；2) 草稿是「填一半」
  的临时态，放本地可零成本上线，也不会把未提交数据写进业务库；3) 菜单维持三个大入口，
  符合果农版导航收敛方向。
- Alternatives：菜单并列「数据导入 / 手工录单」两项（方案 A，不采用：三入口导航被撑到四项）；
  在数据导入页内加「手工录单」选项卡（方案 B，不采用：导入是批处理、录单是长表单，同页互相干扰、
  移动端难用）；草稿落库（不采用：需求只要求「切走能接着填」，落库需新表与清理策略，收益不成比例）。
- Consequences：1) 新增 `frontend/src/views/EntryHubView.vue`、`utils/entryHub.ts`、`utils/entryDraft.ts`
  与 `tests/entry-hub.test.ts` / `tests/entry-draft.test.ts`；2) `AppShell.vue` 导航项结构扩展为
  `ShellNavItem { path; label; icon; matches? }`，后续新增同级入口沿用 `matches`；
  3) 草稿随浏览器存储，换设备或清缓存即丢失，需要跨设备续填时再评估落库。


## ADR-026 — 品牌结算单由「每品牌提示词配置 + 大模型解析」，解析结果经二次确认后入库

- Date：2026-09-16
- Status：Accepted（P0 待开工）
- Context：香香 / 宝贝 / 晴牌等品牌导出的结算单版式互不相同（售后区、清关行、等级写法
  `B3（9KG）` / `B6/7熟` / `C8/9大裂` / `A3（9KG)尾` 均不统一），现有固定模板解析、
  直接把文件写进销售事实的链路已覆盖不了。业务要求「用大模型按品牌解析 → 回填录单界面二次确认
  → 确认后才入库」，且每个品牌只解析自己的文件。
- Decision：
  1) 解析能力按品牌沉淀为**声明式解析配置**（表头映射、明细区识别、等级拆分、售后/费用/清关区
     识别、合计校验），不做模型微调；首个版本覆盖香香 / 宝贝 / 晴牌，润控金象不在本期范围。
  2) **大模型是唯一解析路径**：整张表文本化后连同品牌提示词交给模型，由模型输出结构化槽位 JSON。
     规则/代码只负责归一化（`9-10`→`9/10`）、算数（金额与各项合计）与判定（等级归一、非销售行），
     不承担"猜版式"的抽取职责；模型输出必须通过归一器与校验器才进草稿。
  3) 新增 `POST /api/imports/preview`：入参为品牌 + 文件，返回「录单草稿 + 问题清单」，**不落库**；
     人工确认后仍复用现有 `POST /api/entry` 落库，商号唯一键与覆盖逻辑不变。
  4) 二次确认页沿用录单界面结构（基本信息 / 销售明细 / 售后明细 / 支出费用），问题按
     「行 + 字段」标红并给出原因，人工改完再保存。
  5) 品类拆分口径：等级首字母 → 品种列；数字/区间 → 规格（头数）；`熟/裂/尾` 等后缀 → 备注；
     `B6/7熟` → B、`C8/9大裂` → C。`损/少果`、`验果抽检`、`夹肉/溶` 属非销售行，不计销售金额。
  6) **规格（头数）由整数改为文本**：`sale_record.piece_count` 由 `INTEGER` 改 `VARCHAR(32)`，
     以便原样保存 `6/7` 这类区间；导出仍原样输出。
  7) 解析服务或模型不可用时，页面明确提示不可用并**不进入录单**，不退回手工兜底。
- Why：1) 真实文件写法高度不规范（后缀是开放词表、括号里可能装后缀、括号可能不闭合），
  规则穷举必然失败，抽取必须交给大模型；2) 只解析「本品牌」文件可显著缩小提示词范围、出错时定位清晰；
  3) 归一化与算数交给代码，避免模型改写口径或算错钱；4) 二次确认是客户明确要求的业务闸门，
  也避免模型幻觉直接污染销售事实。
- Alternatives：全量交给大模型解析（不采用：成本高、结果不稳定、回归测试难）；
  为每个品牌写一套硬编码解析器（不采用：版式再变就要改代码，扩展成本高）；
  头数取区间上限并把原文塞进备注（不采用：客户选择原样保留，避免口径被改写）；
  解析后直接入库再让人去改（不采用：模型出错会先污染销售事实）。
- Consequences：1) `piece_count` 改类型需要 `ALTER TABLE`，须在生产库单独安排执行窗口
  （该列不参与任何分析指标，不影响既有看板口径）；2) 新增品牌解析配置目录与预览接口，
  `imports` 从「上传即入库」扩展为「上传 → 预览 → 确认」两段；3) 需要为三个品牌沉淀样例回归集；
  4) 规格（KG）若出现区间（如 `9/10KG`）的处理方式仍需业务确认。

## ADR-027 — 规格（KG）与头数升级为一等分析维度（区间值：原文 + min/max 派生列）

- Date：2026-09-16
- Status：Accepted
- Context：品牌文件里规格与头数是区间写法（`9/10KG`、`6/7熟`），但这两列要参与分析指标。
  若只存一个数值，区间会被抹平且口径无法回溯；若只存文本，聚合要走 SQL 解析文本，
  既慢又没法建索引。此外文件解析写 `spec_raw`、手工录单写 `spec_kg`，两条链路口径不一致。
- Decision：
  1) `sale_record.spec_kg`、`piece_count` 改为文本，存**归一后的规范值**，并新增
     `spec_kg_min` / `spec_kg_max`、`piece_count_min` / `piece_count_max` 派生数值列；
     单元格逐字原文继续留在 `spec_raw` 里，只作溯源。
  2) 归一与解析走唯一入口 `parse_spec_range()`，返回 `(canonical, min, max)`：
     `9/10` 原样保留；`9-10`、`9~10`、`9～10`、`9/10KG`、全角写法统一成 `9/10`；
     端点升序（`10/9` → `9/10`）；单值 `10` 不补 `/`；解析失败留空并在二次确认页标红
     （不可解析即无法进统计）。展示、回显、导出统一用规范值。
  3) 分析分桶统一用归一后的规范文本（`10`、`9/10`），与书写方式无关
     （`9-10`、`９／１０` 一律显示成 `9/10`）；
     标量指标（平均规格 KG、平均头数）按**区间上限**加权计算。
  4) 规格的唯一分析口径收敛到 `spec_kg`，`spec_raw` 仅作溯源与展示；
     `SettlementGradeBreakdown` 的规格分桶一并改走 `spec_kg`。
  5) 文件导入与手工录单都写这三个字段，「导入件没有件数」的旧假设作废。
  6) 开发期不做数据迁移：清库重建后用 `tickets/` 重新导入。
- Why：1) 原文保真 + 派生数值，兼顾可读与可算；2) 保留 min/max 后改口径不用回补历史；
  3) 统一入口能保证两条链路口径一致，避免同一批货在不同页面归到不同桶。
- Alternatives：只存文本、分析时解析（不采用：慢、易错、无法索引）；只存单值（不采用：
  口径被改写且不可逆）；区间拆成两行（不采用：销量会被重复计数）；
  写迁移脚本回填历史数据（不采用：开发期数据可直接重导，脚本成本更高）。
- Consequences：1) 需清库重建并重新导入 `tickets/` 数据；2) 录单 API 的 `head_count` /
  `spec_kg` 由数字变字符串，前端类型、草稿结构、导出同步调整；3) 计算层新增规格/头数维度，
  overview / 单柜诊断 / 货柜对比 / 系列对比 / 顺仔问答 / AI 结论都要跟上；
  4) 规格解析失败成为阻断保存的红项。

## ADR-028 — 结算单导入异常数据的处理口径（客户确认版 A1~A11）

- Date：2026-09-16
- Status：Accepted
- Context：三个品牌的规格写法不统一，我们把 `tickets/` 下 17 个 xlsx 的 501 行销售规格逐行扫描后
  出了一份确认单（`docs/2026-09-16-导入异常数据处理确认单.md`）。客户已对规格类 A1~A11
  逐条给出处理方案；B 组（非销售行）、C 组（表头与结构）尚未全部回复。
- Decision：
  1) **A1 保留 `3/4`**：头数区间原样保留，不展开、不合并。
  2) **A2 归一 `3/4`、`6/8`**：区间里重复的等级字母去掉（`B3/B4` → `3/4`、`C6/C8` → `6/8`）。
  3) **A3 归一 `5/7`**：端点统一升序，`B7/5` → `5/7`。
  4) **A4 保留 `5/7/8`**：三段区间原样保留（不塌缩成 `5/8`），数值端点取最小与最大。
  5) **A5 保留 `9/10KG`、`10/11KG`**：KG 区间原样保留成 `9/10` / `10/11`，
     标量分析按区间上限（`9/10` → 10）计入，两个桶不合并。
  6) **A6/A7/A8/A10 按原建议执行**：去单位、全角转半角、括号可不闭合、
     括号里不是数字时整段当后缀、后缀里的乱码原样保留。
  7) **A9 后缀不参与计算**：后缀（熟/裂/尾/黄皮/硬包/不售后…）整段进备注，
     不单独建列、不进任何指标。
  8) **A11 人工补全**：整行没有 KG 时留空并标红，由人工补齐后再保存；
     **不按品牌默认值自动补**（宝贝 47 行属于这一类，全品牌合计 67 行）。
- Why：A1~A5 的区间写法是客户报价的真实口径，抹平或合并会让「同一批货在不同页面归到不同桶」；

  也不制造看起来合理但实际错误的数字。
- Alternatives：A4 取最小最大（原建议，客户否决）；A9 单独建后缀列（客户否决：增加列但不参与计算）；
  A11 按品牌默认 KG 自动补（客户否决：会导致错误的重量与均价）。
- Consequences：1) `parse_spec_range()` 的规范文本允许三段（`5/7/8`），min/max 仍只取两端；
  2) 二次确认页必须把「缺 KG」渲染成阻断保存的红项；3) 501 行真实规格已冻结为回归集
  （`backend/tests/fixtures/spec_cells_2026-09-16.json` + `backend/tests/test_spec_range.py`）；
  4) B/C 组确认后按同一方式追加 ADR。

## ADR-029 — 品种统计等级改为管理端字段转换规则，取消代码写死 BC→C

- Date：2026-09-17
- Status：Accepted
- Context：新结算单模板会出现 `BC`、`AB` 等组合品种。业务明确：界面展示用户原始写法，
  只有统计看板把 `BC` 归入 `C`；且这个映射未来可能调整，例如把 `AB` 归入 `A`，
  不应再散落在业务代码里写死。
- Decision：
  1) `fruits_ana_admin` 新增 `field_conversion_rule` / `admin_field_conversion_rule` 配置：
     默认种子 `grade:BC→C`，支持新增、修改、启停、删除、排序与操作留痕。
  2) 业务端写 `sale_record` 前统一调用 `field_conversion.convert_grade()`，
     依据启用规则把 `grade_raw` 转成 `sale_record.grade`；`grade_raw` 永久保留原文。
  3) 未命中规则时：`A/B/AB/C/D/E/F` 保留自身，`BC` 等未登记组合归 `OTHER` 并进入问题清单；
     若业务需要 `BC` 独立统计，只需停用 `BC→C` 规则后重新回填或重导。
  4) 等级细分、导出说明、看板等级列表都从动态 `grade` / 转换规则取值，不再内置 BC 别名；
     前端 `Grade` 类型新增 `AB`，聚合标签改为中性 `C果` / `AB果`。
  5) 历史数据迁移不做隐式回填；新导入/手工单即时按当前规则生成，历史等级在后续回填任务中核对。
- Why：1) 组合品种是业务事实，不能靠 `if grade.startswith('BC')` 散落在多端；
  2) 管理端配置比改代码快，且规则变更能留痕；3) 明细原文与统计等级分离，既保真又可追溯。
- Alternatives：继续在业务代码中写死 BC→C（不采用：每次调整都要发版，且前后端、导出多处易漂移）；
  直接拒绝组合品种（不采用：客户已确认 `BC`/`AB` 是真实录入形式）。
- Consequences：1) 需在 MySQL 建 `admin_field_conversion_rule` 表并执行默认种子；
  2) `sale_record.grade` 约束同步支持 `AB`，`backend/scripts/expand_grades.py` 提供可回滚迁移；
  3) 管理端与业务端共享转换表，接口契约和表结构变更需同步两边 model。

## ADR-030 — 新模板多文件导入采用「预览草稿 → 二次确认 → 一次确认入库」

- Date：2026-09-17
- Status：Accepted
- Context：客户新模板已明确为多文件导入，且要求导入后弹出二次确认页：
  回填用户填写值、展示系统计算值、问题行标红、用户可修改；提交仍有问题时再次确认，
  可带错提交，最终以用户提交值为准。旧链路“上传即入库”无法满足这个业务闸门。
- Decision：
  1) 新模板只走 `POST /api/imports/preview`，解析结果写入 `import_job` / `import_draft`，
     不写 `import_batch` / `sale_record` 等正式事实；一个 job 可含多个 draft。
  2) 二次确认页复用录单表单结构，展示 `grade_raw` 原文；问题分 error/warning 标红/标黄；
     保存草稿按行留痕到 `settlement_revision`。
  3) 确认接口 `POST /api/imports/jobs/{job}/confirm` 先校验全部草稿并检查商号冲突；
     无阻断且无冲突时一次写入正式事实；有 error/冲突返回 409，前端二段确认后以 `force=true` 提交。
  4) 正式入库金额/合计必须自洽：销售金额=数量×单价，总件数/销售金额/售后合计/费用合计/
     货款合计/应付金额全部从明细重新求和；文件写的合计原值存 `settlement_summary.file_*`。
  5) 同一 job 内商号重复视为冲突；非 force 直接阻断，force 时按草稿顺序最后一个生效，
     早先重复草稿置为 discarded，避免唯一键 500 与静默覆盖。
  6) 多文件导入仍兼容旧版式上传接口；旧接口继续走原有上传即入库路径，新模板前端改走 preview。
- Why：1) 用户需要“先看再入库”，不能拿正式表当草稿；2) 多文件一次确认比逐文件确认少重复操作；
  3) 文件合计与系统合计分离，才能在不丢原值的前提下修正金额；4) 商号是业务主键，重复导入必须显式处理。
- Alternatives：仍用旧 `POST /api/imports` 多文件直接入库（不采用：无二次确认闸门）；
  每个文件各自 confirm（不采用：多文件场景操作碎片化，且难以保证同批原子性）；
  二次确认不落库只存浏览器（不采用：刷新丢失，无法审计修改与跨会话复核）。
- Consequences：1) 新增 `import_job`、`import_draft`、`settlement_revision` 表及
  `import_batch.import_job_id`、`settlement_summary.file_*` 等审计列；
  2) 导入 API 增加 `/preview`、`/jobs/{job}`、`/jobs/{job}/drafts/{draft}`、`confirm`、`discard`；
  3) 旧 `/api/imports` 保留以兼容既有解析路径与旧测试；4) 需在管理端配置 `BC→C` 等规则后，
  正式统计才按目标等级展示。

## ADR-031 — 用户端与管理端口径一致性修复

- Date：2026-09-18
- Status：Accepted
- Context：用户端与管理端在字段转换目标值、历史等级重算提示、售后金额符号、
  source_type 覆盖保护、商号归一化冲突和录单等级选项上存在口径漂移，可能造成
  静默覆盖、非法等级落库或报表金额符号不一致。
- Decision：
  1) 管理端字段转换规则目标值只允许 `A/B/AB/C/D/E/F/OTHER`；用户端遇到非法规则
     目标值抛出明确 `ValueError`，不再静默归 `OTHER`。
  2) 管理端字段转换页明确提示「规则变更仅影响新导入数据，历史等级不会重算」，
     变更接口操作日志同步记录该提示；不引入后台重算任务。
  3) 售后金额统一按「售后扣减绝对值」处理：保存时统一存非负值，读取、列表导出、
     结算详情与 AI 依赖数据统一返回绝对值。
  4) `import_batch.source_type` 作为覆盖保护条件：导入不能覆盖手工单，手工单不能
     覆盖导入单；同类型覆盖继续走确认流程，并写 `settlement_revision` 留痕。
  5) 保存前检测 `merchant_no_normalized` 冲突；不同原始商号归一化后相同时返回
     conflict / 422，不新增数据库唯一索引。
  6) 管理端录单字段选项允许 `A-F`、`AB`、`BC`，与用户端录单页等级选项一致。
- Why：1) 非法转换目标会造成统计等级不可解释；2) 历史等级重算涉及全量数据迁移，
  低风险方案是显式提示而非后台任务；3) 同一字段同时存在负值和正值会让报表与导出
  产生相反符号；4) 静默跨来源删除会丢失审计链；5) 展示归一化不能替代业务唯一性校验。
- Alternatives：后台自动重算历史等级（不采用：需要迁移与长时间任务）；为
  `merchant_no_normalized` 增加唯一索引（不采用：需要数据库迁移）；继续允许跨
  source_type 静默覆盖（不采用：审计和业务归属不可追溯）。
- Consequences：1) 历史遗留负售后金额在读取/导出时按绝对值展示，新写入值统一非负；
  2) 管理端非法转换目标被后端 422 拒绝；3) 跨来源覆盖与归一化冲突改为显式冲突，
  调用方需按现有冲突流程处理；4) 相关旧测试期望已同步修正。

## ADR-032 — 品牌对比选择器增加「品类」前置层级

- Date：2026-09-18
- Status：Accepted
- Context：品牌对比页的结算单选择器此前按 ADR-019 分为「品牌 → 结算单」两步；

- Alternatives：继续两步选择并在品牌列表里混合品类（不采用：多品类时品牌列表语义不清）；
  直接让品类参与品牌对比聚合（不采用：本期对比仍以品牌为聚合粒度）。
- Consequences：1) `/api/settlements` 响应契约增加 `fruit_type`，前端类型与归一化同步；
  2) 选择器交互从两步变为三步；3) 当前数据以「榴莲」为主，界面会先展示单品类再进入品牌列表。

## ADR-033 — 结算单详情与基础口径术语收口

- Date：2026-09-19
- Status：Accepted（开发中）

  `goods_amount`，前端 `SettlementSummary` 增加 `goodsAmount`；详情页当前改用 `fee_amount`

## ADR-035 — 文件导入售后内容向上填充

- Date：2026-09-19
- Status：Accepted
- Context：新结算单模板中，售后明细的内容列存在合并单元格场景，当前行内容为空时，
  应沿用上一行内容，和销售明细日期列的空值向上填充逻辑保持一致。
- Decision：
  1) `_parse_after_sales` 在售后区块逐行读取时维护“最近一条非空内容”。
  2) 当前行内容为空、但摘要或金额任一非空时，内容取最近一条非空内容。
  3) 内容、摘要、金额全部为空的行跳过，不生成售后明细，也不更新继承值。
  4) 售后首行内容为空且无上一行可继承时，保留空内容，由后续草稿校验报
     “售后内容不能为空”。
  5) 金额、摘要、汇总与入库绝对值逻辑不变，仅补内容。
- Why：售后合并单元格只填写一次内容，后续空内容行需要继承同一售后事项，否则会丢失明细。
- Alternatives：要求用户在 Excel 中拆开合并单元格（不采用：增加人工操作）；
  直接复制销售日期填充逻辑并限制只有金额非空才填充（不采用：摘要也可能单独存在）。
- Consequences：1) 空内容且无金额/摘要的空白行仍被忽略；2) 相关回归测试已补。

## ADR-036 — 业务端侧边导航名称与图标由管理端菜单驱动

- Date：2026-09-20
- Status：Accepted
- Context：管理端「菜单管理」可以改名，但业务端 `AppShell.vue` 的导航是硬编码常量，
  前端与后端都不读 `admin_menu`，导致改名在业务端永远不生效。排查中同时发现管理端
  `seed._seed_menus()` 按「名称 + 父级」匹配已有菜单，管理员改名后重启会补建一条
  同名旧菜单，出现两条 `/overview`。
- Decision：
  1) 管理端种子改按稳定标识匹配菜单：权限码 → 路由路径 → 同级同类排序 / 同名兜底；
     命中后保留管理员维护的名称（种子只补缺，不回写）。
  2) 业务端新增只读模型 `AdminMenu` / `AdminRoleMenu`，只查询不创建、不修改。
  3) `GET /api/auth/me`（以及 login / register）的 `UserRead` 新增 `menus` 字段，
     返回当前用户被授权菜单的 `route_path / name / icon / permission_code / sort_order / is_active`。
  4) 业务端导航的「位置」仍由前端槽位决定（主导航 3 个大入口 + 更多 + 仅页签项），
     避免管理端误加菜单把移动端底部导航挤坏；管理端菜单只覆盖**名称、图标与启用状态**。
  5) 槽位命中菜单且 `is_active=false` 时整项隐藏；未命中菜单的槽位保留本地兜底文案
     与既有权限判断，保证未授权用户导航不整块消失。
  6) 图标名只在前端白名单 `SHELL_ICONS` 内解析，不做任意字符串的动态组件渲染。
  7) 合并规则抽到 `frontend/src/utils/shellMenu.ts`，便于单测覆盖。
- Why：把「导航位置」和「菜单文案」分开，既让管理端改名立即生效，又不破坏已确认的
  果农版导航结构与权限行为。
- Alternatives：业务端侧栏完全按 `admin_menu` 目录树动态渲染（不采用：会推翻已确认的
  「3 个大入口」设计，且目录层级变化会直接影响移动端布局与页签归属）；
  只做文档说明不改代码（不采用：管理员无法自助改名）。
- Consequences：1) 管理端新增菜单不会自动出现在业务端，需前端补对应路由与槽位；
  2) 停用菜单会隐藏业务端入口；3) 未命中菜单时仍显示本地兜底项。

## ADR-037 — 手工录单暂存由浏览器 localStorage 改为数据库存储

- Date：2026-09-20
- Status：Accepted
- Context：手工录单的「暂存」原按 ADR-025 写入浏览器 `localStorage`，但页面刷新时只有
  URL 带 `?draft=1` 才会恢复，普通刷新 `/entry` 会跳过读取；同时换设备或清缓存会丢草稿。
- Decision：
  1) 新增 `entry_draft` 表，按 `user_id` 唯一保存一份手工录单草稿，`payload` 使用
     `PARSE_PAYLOAD`（MySQL MEDIUMTEXT）存完整表单 JSON。
  2) 新增 `/api/entry/draft`：`GET` 读取、`PUT` 覆盖保存、`DELETE` 清除，均要求登录。
  3) 前端 `/entry` 普通刷新也读取草稿；编辑已有结算单时仅恢复 `editing=true` 且
     `merchant_no` 匹配的草稿，避免用新单草稿覆盖已保存数据。
  4) `/imports` 的「继续录单 / 重新录单」卡片改从 `/api/entry/draft` 读取与清理。
  5) 仍保留 800ms 防抖自动暂存，失败时静默降级为“只影响刷新后续填”，不影响录单主流程。
- Why：数据库存储能跨浏览器和刷新恢复，符合当前“暂存”预期；草稿仍不与正式结算单共用，
  不进入销售事实与分析链路。
- Alternatives：继续用 `localStorage` 并放开刷新读取（不采用：不解决换设备丢失）；
  把草稿写入 `import_draft`（不采用：`import_draft` 是文件导入确认前的解析草稿，语义不同）。
- Consequences：1) 需在启动时由 `Base.metadata.create_all` 创建 `entry_draft`；
  2) 暂存请求会在用户输入时触发，后续若网络较差可把自动暂存改为仅按钮触发或增加请求合并；
  3) 历史 `localStorage` 中的旧草稿不再展示。
