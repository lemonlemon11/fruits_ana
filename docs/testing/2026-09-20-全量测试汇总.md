## 四、中途结果不可用的原因（已排除代码缺陷）

- 现象：同一份测试在本轮内出现多种结果：最初 3 失败（本轮已修）→ 27 项 ERROR/FAILED → 13 项 → 又变，
  失败项在 `test_auth_api`、`test_ask_api`、`test_analytics*`、`test_settlements_api` 之间漂移。
- 关键证据：**多个 pytest 进程共用同一个 sqlite 测试库**（`backend/.pytest-tmp/fruit-analysis-test.sqlite3`）。
  18:15 起另一个会话在同一仓库、同一 `--basetemp` 上运行 3 轮全量 pytest（进程命令行：
  `for i in 1 2 3; do .venv/bin/python -m pytest backend/tests -q --basetemp=backend/.pytest-tmp ...`）；
  本会话 18:05–18:14 也在跑同一套命令。
- 报错形态符合「跨进程 drop / create 交错」：
  - `DROP TABLE admin_notification_recipient` → `no such table: admin_notification_recipient`（另一次运行已先删除）
  - `create_all` 期间 `no such table: main.admin_notification`（建表被并发 drop 打断）
  - `table user already exists`（并发创建）
  - 连带 `no such table: import_batch` / `no such table: sale_record`，使与断言无关的用例一起失败
- 结论：这些失败出现在夹具建表阶段、且随并发运行变化，**属于共享测试库争用，不是代码缺陷**。
- 反证（排除「模型/表结构损坏」）：在**独立临时库**上执行 `Base.metadata.create_all()` / `drop_all()`
  均成功（25 张表），说明当前模型元数据本身可以正常建表，失败来自共用同一个 sqlite 文件。
- 最终结论：并发结束后（18:19:48–18:21:09）清空测试库串行重跑，**后端全量 375 项全部通过、退出码 0**
  （`--junitxml` 复核：`testcase` 375 条、`failure`/`error` 0 条）。
  中途那些「失败数」不代表当前代码质量，不能作为缺陷清单使用。
- 另一个客观事实（非阻塞项，但需注意）：测试期间 `backend/app/models.py`（18:00）、
  `backend/app/api/auth.py`（18:01）、`backend/app/auth.py`、`backend/app/schemas.py`（18:03）被其他会话修改，
  工作区处于在途状态。
- 建议：给仓库约定 **每次运行使用唯一 basetemp**（如 `--basetemp=backend/.pytest-tmp-$USER-$RANDOM`），
  或串行化多会话测试，避免共用同一 sqlite 文件。
