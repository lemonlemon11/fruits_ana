## 二、P0 — 上线阻塞

### P0-1 `.xls`（Excel 97-2003）文件 100% 导入失败，且报错不可读

- **现象**：上传 `.xls` 返回失败，界面只显示「导入文件失败」，无具体原因。
- **证据**：
  - `tickets/润控金象/4车鲁PBB982【润控金象】榴莲1792件 CICU5985740结算单.xls`
  - `tickets/香香/香香榴莲-8.xls`
  - 解析层异常：`ImportError: \`Import xlrd\` failed. Install xlrd >= 2.0.1 for xls Excel support`
- **根因**：
  1. `backend/app/parser/settlement_parser.py:159` 明确把 `xls` 当作受支持格式，但
     `backend/pyproject.toml` 只声明了 `openpyxl`，未声明 `xlrd`；`.venv` 内也确实没有 `xlrd`。
  2. `backend/app/api/imports.py:126` 只捕获 `BadZipFile/OSError/UnicodeError/ValueError`，
     `ImportError` 落到兜底分支，用户只能看到「导入文件失败」。
- **影响**：客户只要交一份老格式 `.xls` 就导入不了，且现场无法自助判断原因（真实样本占比 2/19）。
- **建议**：
  - 方案 A（推荐）：`backend/pyproject.toml` 增加 `xlrd>=2.0.1`，并补 1 条 `.xls` 解析用例；
  - 方案 B：明确不支持 `.xls`，在上传校验处直接返回可读提示「请另存为 .xlsx 后上传」。
  - 无论选哪个，都应把 `ImportError` 显式映射成可读失败原因，不再走兜底文案。

### P0-2 真实单据中的「非 A/B/C 行」被静默丢弃，导致件数与金额少算

- **现象**：明细件数/金额小于结算单实际，用户看到「总件数差异」红字提醒却无从解释。
- **证据（同一份文件内逐行核对）**：
  - `香香/647结算单（香香L-009RXRK01)(1).xlsx`：等级列写「霉果」的行，数量 3、单价 100、金额 100
    → 等级落 `OTHER`，该行不写入销售事实（少 3 件），同时报 `amount_mismatch`（3×100≠100）。
  - `香香/642结算单（宝贝L005）(1)+清关(2).xlsx`：数量列为「散果」的行，单价 330、金额 330
    → 数量解析失败，整行丢弃（少 1 件 / 330 元）。
  - `香香/646结算单（香香L007)(3).xlsx`：金额列写「补售后」的行（规格 A3(10KG)，数量 1）
    → 报 `invalid_numeric` error，行被丢弃（少 1 件）。
  - `香香/638结算单（香香L-004)`：同类「补售后」行 1 条，报 `invalid_numeric`。
- **根因**：解析器对「非等级文本 / 中文备注占位单元格」一律判为无效数值并丢弃整行
  （`parser/settlement_parser.py` 的 `_parse_rows`）；导入结果只用 `data_issue` 记录，
  页面未汇总「已跳过多少行、合计多少件、多少元」。
- **影响**：数据失真且不可追溯——用户按摘要口径对账必然对不上；「霉果/散果/补售后」是
  真实业务语言，不是脏数据。
- **建议**：
  1. 先与业务确认口径：这类行分别应归入「C 果」「售后扣减」还是「不计入」；
  2. 导入结果摘要中显式输出「跳过 N 行 / 合计 X 件 / Y 元」并提供明细下载；
  3. 数值列出现中文时，先按「同一行数量×单价」或摘要口径回算，而不是直接丢行。

### P0-3 文件内部商号与文件名不一致，存在误覆盖（覆盖已有结算单）风险

- **现象**：`tickets/香香/646结算单（香香L007)(3).xlsx` 文件名叫「646」，文件内 `商号：635`，
  `单号：香香L007`，`来货数量 1980 件`（明细 1973 件）。
- **根因**：商号（`merchant_no`）是唯一业务键（ADR-016），文件名不参与身份判定。
  若 635 已导入过，本次上传会命中冲突并提示覆盖；确认覆盖后 **635 的原有数据被替换**。
- **影响**：一旦是填单方笔误，会覆盖另一张结算单的真实数据（本次已被误删数据教训过，见 ADR-021）。
- **建议**：业务侧先确认该单归属；必要时在上传确认弹窗中并列展示
  「文件名 / 文件内商号 / 单号」，让用户一眼看出不一致再决定是否覆盖。

## 三、P1 — 重要（上线前需给出结论）

### P1-1 润控金象两种真实版式完全不支持

- **证据**：
  - `tickets/润控金象/QAA00015.xlsx`：版式为「进销存明细表」，表头为
    `销售日期/销售单号/销售人/货号/品名/计价方式/销售数量/单位重量(斤)/销售重量(斤)/单价(元)/包装费(元)/其他费用(元)/货款(元)/成本价格(元)/...`；
    解析结果 `SettlementParseError: 缺少商号，无法确定结算单身份`。
  - `tickets/润控金象/批发-广州煜谦结算单_EMCU5313427.xlsx`：版式为「代卖结算报表」，
    含 `供应商/到货日期/柜号/采购件数/采购单/车牌号` 与明细
    `品类/品牌/规格/品种/组成单位/销售数量/单价/金额/备注`；
    同样因缺「商号」失败。
- **附加发现**：这两份都没有独立等级列，等级信息混在品名 / 规格里
  （如品名「金象越南金枕小箱 A 果榴莲」「B+榴莲」，规格「A3」「B3」）；
  且存在 `单价 0 元` 的「补客户 / 报损 / 试吃 / 补损 / 来货少果」行。
- **建议**：确认这批供应商是否在系统范围内。
  - 在范围内：需要新增版式适配器 + 等级抽取规则（从品名/规格识别 A/B/C），并明确 0 元行口径；
  - 不在范围内：在上传说明中明确「仅支持本系统标准结算单版式」，避免用户反复试错。

### P1-2 金额与「数量×单价」不一致时只告警、不阻断，且以文件金额为准

- **证据**：`香香/647...xlsx` 第 28 行 `3 × 100 = 300`，文件金额列写 `100`，仅记录
  `amount_mismatch (warning)`。
- **影响**：成交均价、销售额会被这类行拉低，且普通用户看不到 warning。
- **建议**：明确「以金额为准还是以单价×数量为准」，并在页面把 warning 提到导入结果摘要中。

### P1-3 同一份结算单重复上传（字节完全一致）依赖内容哈希去重

- **证据**：`tickets/香香/638结算单（香香L-004)(1)(1).xlsx` 与 `(1)(1)(1).xlsx` 的 SHA-256 完全相同。
- **建议**：确认界面在「重复文件 / 同商号冲突」两种情况下的文案能区分，避免用户以为系统丢单。
