# 结算单新模板导入与二次确认设计

- 日期：2026-09-17
- 状态：待用户复核书面设计；未实施、未迁移数据库
- 样本：`attachments/结算单模板样式-测试数据 1.xlsx`、`2.xlsx`、`3.xlsx`
- 关联：ADR-002、006、008、015、016、020、026～028；取代尚未批准的
  `2026-09-16-settlement-import-schema-design.md` 中不再适用的严格拒收、禁用 BC 等提议。

## 目标与边界

用户上传新模板后，系统解析并回填到现有手工录单表单。表单并排展示原填写值与系统计算值，
标出问题及原文件行号，允许修改输入值。计算项随输入联动，确认前再由后端重新校验。
**正式入库的计算字段必须自洽**，不能保留明细与汇总错位；原值及修正原因仍须可追溯。

本次包含固定新模板解析、录单表单的导入确认模式、销售与结算模型、统计等级口径、
手工录单同源计算、API 与回归验证。不改变历史上传文件，不直接清空或重建运行中的 MySQL。
旧品牌非标准文件和已有 AI 解析的去留需按来源分流，不因新模板上线而删除在途功能。

## 确认的业务口径

| 字段/分区 | 保存、计算与校验 |
| --- | --- |
| 商号 | 业务唯一身份；保留原文，用规范键检测空白及“单”前缀差异；柜号可重复。内部 `id` 仍作数据库主键。 |
| 单号 | 保留原文，去空格并识别横杠得到展示值与品牌/编号；不把柜号或单号当唯一键。 |
| 转运公司、市场 | 前者实填车牌号；市场为下拉控件，选项来自 `fruits_ana_admin`。原文含“江南”或“海吉星”时按包含匹配选中已配置市场，并保留原文用于溯源。 |
| 到达日期、来货数量 | `DATE` 与件数值；来货数量与销售总件数不强制相等，差异作为提示。 |
| 销售日期 | 同一日期后续空格继承最近一次日期；确认页把继承后的实际日期回填到每一行，不显示“同上”。首个销售行缺日期须人工补填。 |
| 品种 | 确认页始终显示原文 `BC`/`AB`；统计代码按 `fruits_ana_admin` 字段转换规则动态生成。默认种子 `BC→C`，`AB` 不配置则保持 `AB`。原文永久保留。 |
| 头数、KG、备注 | 头数保留 `3/4`、`3/4/5`、`3/5` 等规范文本；KG 允许小数；备注保留原文。 |
| 数量、单价、金额 | 数量接受数字及去空格后的数字文本；单价空白取 0。显示原金额（空白取 0），确认表单金额按 `数量 × 单价` 自动修正。 |
| 总件数、销售金额 | 分别由**销售数量求和**、已修正销售金额求和；原文件合计只用于对照，不写入正式统计值。 |
| 售后 | 内容、摘要与非负扣减金额逐行保留；金额空白取 0，合计为金额求和。当前模板无售后数量/单价列，不臆造其乘积。 |
| 货款合计 | `销售金额 - 售后合计`。 |
| 费用 | 自定义摘要及 0 金额行保留；空金额取 0，费用合计为金额求和。 |
| 应付金额 | `货款合计 - 费用合计`；原文件值仅用于对账。 |

金额使用后端 `Decimal` 按人民币分四舍五入；计算前保留原始文本与来源行。件数按当前
`NUMERIC(18,4)` 接收合法数字，不把文本数字误判为空；精度超限与非数字标为必须处理。
金额空白虽然在原文栏显示为 0，但如果数量与单价算出非零，确认表单仍显示计算值。
销售数量、头数和 KG 必须大于 0，单价、售后及费用金额允许为 0、不得为负；
来货数量允许为 0。应付金额可因费用大于货款而为负，不擅自钳制。

### 品种口径

`sale_record.grade_raw` 是用户确认页与原文件中的写法，`sale_record.grade` 是用于分析的代码。
导入核对页、手工录单页、结算单详情和导出始终展示用户原始录入值：录了 `BC` 就显示 `BC`，
只有统计、看板、品牌对比、AI 数据包等分析链路使用转换后的 `grade`。
`grade` 由 `fruits_ana_admin` 的字段转换规则动态决定；代码不写死 `BC→C`，也不默认拆 `AB`。
系统默认种子规则为 `BC→C`，管理员可停用、修改或新增规则（例如把 `AB→A` 后统计就按 A 展示）。
未命中规则的原文若本身是 `A/B/AB/C/D/E/F` 则保留原文，其余归 `OTHER` 并标为待人工处理。
所有动态等级列表、数量占比、金额占比、按等级号别细分、品牌对比和导出沿用同一映射。
历史记录先用可辨识的 `grade_raw` 回填新等级列；无法确定的记录保留原分析结果并列入核对清单。

### 品种转换配置（fruits_ana_admin）

将“原文品种 → 统计品种”从硬编码改为管理端可维护的字段转换规则，只影响分析统计，
不改变录入页展示。默认规则为 `BC → C`；`AB` 不预置规则因此默认独立。
若后续配置 `AB → A`，统计、看板、品牌对比、导出和 AI 数据包都动态按 A 展示，录入页仍显示 `AB`。
管理端配置页至少包含：字段名、原始值、目标值、启用状态、生效顺序和说明；
后端统一读取该规则生成 `sale_record.grade`，未命中规则的原文保留原值并标为待处理。
该配置暂不实施数据库迁移，等视觉审核通过后再进入 `fruits_ana_admin` 开发。

## 导入与确认流程

1. 上传文件，按区块标签和列名定位表头及可变长明细；读取 Excel 值与公式缓存但不用缓存作为
   统计依据。结构不匹配要提示具体标签/行号，不错误地写入业务表。
2. 将原始文件、解析原值、规范化结果和问题生成独立草稿；此时看板和结算单列表不可见该单。
   同一用户可重新打开未确认草稿，不与本地手工录单草稿互相覆盖。
3. 在现有手工录单表单开启“导入核对”模式：回填基本信息、销售、售后、费用；错误行与字段
   标红，显示原值、修正值、来源行号和原因。汇总区并排显示原文件合计及系统最新计算值。
   修正数量/单价/售后/费用后实时重算，用户不能直接输入一个与明细不符的汇总值。
4. 点击“确认提交”时服务端再次计算并返回剩余问题；**计算差异必须先自动修正为当前公式
   结果**。无法推断的日期、品种、数量等结构性错误须人工修改，不将其变成 0 参与分析。
5. 如果出现过自动修正或仅余不影响计算的提示，弹窗列出原值、修正值和剩余提示，
   询问“文件存在问题，是否以当前修正结果提交？”；再次确认后同一事务提交批次、明细、
   售后、费用、汇总及问题记录。原文件无问题且用户未改值时正常确认。
6. 商号冲突展示既有单据并取得单独覆盖确认；确认前旧单仍可查，覆盖失败保持旧单与原文件。

所有用户修改都必须留痕：确认提交和后续手工修改，记录单据标识、修改人、修改时间、来源分区、
来源行、字段、原值、最终值、修改原因和问题类型；计算值修正也记录“系统自动修正”原因，
确保审计时能还原原始录入与最终入库之间的每一次变化。

此流程按最后一次用户确认收敛：**“可带问题确认”适用于可追溯的非计算提示，不适用于仍然
不自洽的计算字段**。已有的“原样错误金额照常参与看板”提议不实施。确认后的金额与总件数
来自用户最终确认的输入字段及统一公式，而非上传文件里过期的合计值。

## 持久化设计

| 表 | 变更 |
| --- | --- |
| `import_draft` | 保留原始解析载荷、正在编辑的载荷、源文件引用及哈希、状态、版本号、修改人与确认人/时间；确认后保留原值与修正痕迹以供追溯。 |
| `import_batch` | 保留既有内部主键、原始商号/规范商号、柜号、原始/规范单号；记录确认人、时间及“正常/含提示”状态。规范商号用于检测逻辑重复，未完成冲突清点前不直接新增唯一约束。 |
| `sale_record` | `grade_raw` 留原文；分析用 `grade` 支持 `AB` 和转换规则生成的值，默认 `BC→C` 由配置表驱动；数量、单价、金额为最终确认值；保留来源行号。头数文本、KG 及其派生端点继续服务现有规格分析。 |
| `settlement_after_sale_item`、`settlement_fee_item` | 导入与手填共用明细表，保留顺序、金额 0 和来源行号；由明细求和。 |
| `settlement_summary` | 现有金额字段存**确认后计算值**；增加原文件填写的总件数、销售/售后/货款/费用/应付合计等审计字段和差异状态。金额明细不与汇总重复计算成独立事实。 |
| `data_issue` | 记录来源行、字段、原值、修正值、问题类型、严重度、处理人及状态；确认后仍保留已修正的计算问题以追溯原因。 |
| `settlement_revision` | 统一修改留痕表：记录批次/商号、草稿版本、分区、来源行、字段名、原值、最终值、修改类型（人工/自动）、修改人、修改时间及原因；确认页修改和后续手工修改都写入。 |
| `source_file` | 继续保存文件名、哈希与原件路径，避免修改后的录单遮蔽原始依据。 |

索引：正式批次继续有商号唯一键；销售表按 `(sale_date, grade)` 与 `import_batch_id`
查询；草稿按 `(created_by, status, updated_at)` 查找待办，确认时用版本号防止并发覆盖。
规范商号唯一约束须先扫描历史冲突、确定合并/保留规则，再通过迁移添加，不能直接重建库。

## 分析、接口与错误边界

- 看板、品牌对比、结算单对比、详情、导出与 AI 数据包都从同一批已确认的 `sale_record`
  取值，`grade` 全部由字段转换规则动态生成；全单汇总与按日期/等级分解均可相加一致。
- 预览接口返回草稿 ID、版本号、可编辑载荷、原值/计算值、带 `section/row/field/code`
  的问题数组；更新草稿时返回重新计算结果；确认接口须提供版本与冲突覆盖确认，版本过期
  返回冲突，不采用前端自行计算的金额作最终事实。
- 金额/合计修正、文件公式缓存不可用为可自动修正项；日期/数量/等级无法解析、无商号等为
  阻断项；市场名称变体、来货量与销售量不等这类不影响计算的问题为可带入库提示。
- `POST /api/imports` 既有调用与 `/api/entry` 手填路径需要兼容旧客户端；新核对链路使用
  明确的预览/草稿/确认动作，不在上传时顺手创建正式批次。字段改变同步后端 schema 与前端
  `api/types.ts`、`normalize.ts`、`client.ts`。
- 原文件仍由服务端保存。确认失败不清理仍在使用的原件；放弃草稿和已确认数据的保留期、
  文件清理必须避免删除被其它批次引用的哈希文件。

## 迁移与验收

仅提供可审查、可回滚的 schema 迁移与历史数据核对步骤；本设计审批不授权执行线上 DDL、
删除旧表或清库。先备份、检查旧等级/商号冲突和旧 AI 缓存，再迁移与回填；数据口径变更
追加新 ADR，保留旧 ADR 的历史记录，并同步架构、交接与用户手册。

- 三份新样本要能解析到商号、销售与费用；原文件的数量公式缓存均为 0，但按销售数量求和
  为 `2000 / 1000 / 2500`；样本 2/3 的手填总件数 `2000` 与真实明细差异须标红并自动修正。
- 样本 1 首行空单价以 0 计；销售金额、售后/费用和应付金额重算后逐项一致。
- 以 `AB`、`BC` 构造明细，表单展示原写法；默认配置下 `BC` 归 C、`AB` 保持独立；
  修改 `AB→A` 等规则后统计、看板与导出应跟随规则变化，等级件数之和、总件数及销售金额之和均一致。
- 修改数量、单价和费用后即时更新行/汇总；仍有阻断项时不能提交；仅有提示时需要
  二次确认并保留问题；放弃草稿不污染正式数据。
- 同商号覆盖、并发修改草稿、手工录单回显、导出及旧数据分析都需回归。

## 待用户书面复核的边界

上述自动修正与强制自洽按最后确认优先于之前“错误金额可原样提交”的讨论。
当前模板的售后仅有金额列，按直接填写金额处理；来货数量与销量不等只提示。
若业务对这两条或对未列出的组合品种另有口径，实施前应修改本文并取得确认。
