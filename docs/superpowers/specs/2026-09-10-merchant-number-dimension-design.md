# 商号维度重构与数据明细页设计

日期：2026-09-10
状态：待用户确认
取代：`2026-09-10-settlement-number-identity-design.md`（原方案以「单号」为唯一键，已被本次业务规则修正）

## 背景

现有系统的查询与展示以「柜号」为维度，但真实业务存在两张结算单共用同一柜号的情况
（样例中 `单637` 与 `640` 均为 `CBHU2970762`），柜号无法唯一标识一张结算单。业务方给出四条规则：

1. **商号**：我司记录的商业合同唯一单据号 → 唯一键。
2. **单号**：客户侧单号 → 允许重复。
3. **柜号**：车柜标识 → 允许缺失。
4. **转运车号**：运输车车牌号 → 允许重复。

## 目标

- 以「商号」作为结算单业务唯一键，替换「柜号 + 文件哈希」的身份口径。
- 新增「数据明细」页：按结算单查看所有已导入单据及关键指标，可展开单张单据的全部明细。
- 现有以柜号为查询维度的展示与查询，全部改为以商号维度查询。

## 非目标

- 不引入结算单与柜号的一对多拆分（一张结算单仍视为一个柜号下的完整结算）。
- 不改动等级口径（`BC` 归入 `C`）、金额校验逻辑与导入问题明细机制。
- 不做分页与大数据量优化，当前单据量级为十位数。

## 术语与字段映射

| 业务名 | 字段 | 来源（Excel） | 唯一性 | 可空 |
| --- | --- | --- | --- | --- |
| 商号 | `merchant_no` | `B5` 标签「商号：」右侧单元格 | 全局唯一 | 否 |
| 单号 | `order_no` | `B7` 标签「单号：」右侧单元格 | 允许重复 | 是 |
| 柜号 | `container_no` | `B6` 标签「柜号：」右侧单元格 | 允许重复 | 是 |
| 转运车号 | `vehicle_no` | `B8` 标签「转运公司：」右侧单元格 | 允许重复 | 是 |

规范化规则：只做 `strip`，保留原始写法（例如 `单624` 不去掉「单」前缀）；唯一性判断基于
规范化后的值，重复商号即视为同一张结算单。文件哈希不再作为业务身份，仅用于原始文件留存与去重提示。

## 数据模型变更

`ImportBatch`（承担「结算单」职责）

- 新增 `merchant_no`（`String(128)`，`NOT NULL`，唯一索引 `ux_import_batch_merchant_no`）。
- 新增 `order_no`、`container_no`、`vehicle_no`（`String(255)`，可空）。
- 保留 `file_name`、`imported_at`、`status`、计数与 `error_summary`。

`SaleRecord`

- 移除 `container_id`、`container_name`：柜号属于结算单级信息，通过 `import_batch_id` 关联取得，
  避免同一单据在每行重复存储。
- 保留 `import_batch_id`（结算单归属）作为唯一维度关联；其余字段不变。

`ContainerSummary` → `SettlementSummary`

- 表名 `container_summary` → `settlement_summary`，改为按 `import_batch_id` 唯一。
- 移除 `container_id`、`container_name`，字段（销售金额、售后合计、货款合计、费用合计、
  费用明细、清关税费、应付金额、备注）保持不变。

## 导入与冲突处理

- 解析阶段新增结算单级元数据：商号（缺失即文件级错误）、单号、柜号、转运车号。
- 柜号缺失不再产生行级错误；仍要求每行有销售日期、数量、单价/金额与可识别等级。
- 导入流程：先解析商号 → 查询是否已存在同商号结算单：
  - 不存在：正常写入。
  - 已存在且未确认覆盖：返回 `conflict` 状态与既有结算单信息，数据库不变。
  - 已存在且确认覆盖：新数据校验通过后，在一个事务内替换旧结算单（旧明细、旧摘要、
    旧问题记录一并删除），再写入新数据；失败则整体回滚。
- 覆盖后清理不再被引用的旧原始文件。

## API 契约

新增

- `GET /api/settlements`：数据明细列表。参数 `start_date`、`end_date`、`merchant_no`（可选）。
  未传日期时按默认范围计算：`[最新销售日期 - 1 个月, 最新销售日期]`，含两端，并在响应中回传实际生效范围。
  返回每张结算单一行：`merchant_no`、`order_no`、`container_no`、`vehicle_no`、
  `sale_date_start`、`sale_date_end`、`sales_amount`、`grade_quantities`（A/B/C 件数）、
  `total_quantity`、`average_price`、`record_count`；按最近销售日期倒序。
- `GET /api/settlements/{merchant_no}/records`：该结算单的全部销售明细（日期、品种规格、
  等级原文与标准等级、数量、单价、金额、备注），供「查看明细」使用。

调整

- `GET /api/analytics/container-comparison` → `GET /api/analytics/settlement-comparison`，
  以商号为对比主体，柜号/单号/转运车号作为辅助展示字段。
- `GET /api/analytics/containers/{container_id}` → `GET /api/analytics/settlements/{merchant_no}`。
- 通用筛选参数 `container_id` → `merchant_no`；`overview`、`trend` 同步替换。
- `GET /api/exports/overview.csv` 与单柜导出改为按商号导出结算单数据。

移除兼容别名：内部系统单一部署，重命名后直接切换，不保留旧路径（避免两套口径并存）。

## 前端

导航改为四项：`销售总览` `/overview`、`数据明细` `/settlements`、`商号对比` `/settlement-comparison`、
`数据导入` `/imports`。

数据明细页

- 顶部筛选：销售日期范围（默认最新销售日期往前一个月）+ 商号关键字。
- 表格列：商号、单号、柜号、销售日期（区间）、销售额、A/B/C 销售件数、平均售价
  （销售额 ÷ 总件数）、操作。
- 操作列「查看明细」：打开弹窗，展示该结算单全部明细行（日期、品种规格、等级、数量、单价、金额、备注）。
- 空状态区分「范围内无数据」与「尚未导入任何单据」。

商号对比页 / 商号详情页

- 对比页以商号作为选择与列表主体，柜号、单号、转运车号作为辅助信息展示；默认仍为最近两张单据，
  最多三张。
- 详情页改用商号作为路由与查询身份，展示该结算单的等级指标、趋势、异常与结算摘要。

## 数据回填与迁移

脚本 `backend/scripts/backfill_settlement_identity.py`（幂等）：

1. 迁移表结构：`import_batch` 增加结算单字段与唯一索引；`sale_record` 删除柜号列；
   `container_summary` 重命名为 `settlement_summary` 并按 `import_batch_id` 唯一。
2. 遍历 `import_batch`，读取 `source_file.storage_path` 指向的原始文件，重新解析结算单级元数据，
   回填 `merchant_no`/`order_no`/`container_no`/`vehicle_no`。
3. 校验：商号非空且唯一；回填后销售明细行数与金额与迁移前一致；缺失原始文件的批次直接报错退出。
4. 迁移前把受影响表的数据导出到 `backend/data/` 下的 SQL 快照，便于回滚（该目录已被 Git 忽略）。

## 测试与验收标准

- 解析：从样例文件读取 `B5/B6/B7/B8` 四个字段；柜号缺失不报错；商号缺失报文件级错误。
- 导入：同商号再次导入返回 `conflict` 且数据库不变；确认覆盖后仅保留新数据；覆盖过程失败整体回滚。
- 列表 API：默认范围为最新销售日期往前一个月且含两端；返回 A/B/C 件数、销售额与平均售价；
  商号筛选与日期筛选生效；范围内无明细的单据不返回。
- 明细 API：返回该商号全部明细行，商号不存在返回 404。
- 对比/详情 API：以商号返回正确指标，柜号相同的两张单据可分别查询且互不干扰。
- 回填脚本：对现有 4 张单据执行后，商号为 `单624`、`626`、`单637`、`640` 且唯一，明细行数保持 86。
- 前端：四项导航可切换；数据明细页默认范围正确、列与弹窗明细完整；商号对比可选中 2~3 张单据；
  `npm run build` 与前端测试通过。

## 风险与权衡

- 移除 `SaleRecord.container_id` 会同时改动解析、导入、分析与导出，属跨层重构；收益是维度唯一
  （结算单），避免柜号在明细层形成第二套口径。
- 商号缺失的历史文件无法回填，脚本选择直接失败而不是静默写入空值。
- 覆盖式导入会删除旧明细，用户确认前的 `conflict` 返回必须保留既有数据不变。
- 与并发会话的前端改动存在冲突风险，实施期间前端文件应串行修改。
